# Changelog

Each framework release says what a consumer app must change in its own files. Releases use semantic versions: a major release means a consumer must change its own files, a minor release adds rules or roles a consumer can adopt without edits, and a patch changes wording only.

## Unreleased

## 7.0.0 (2026-11-23)

It is a major release because a consumer changes its own files: its `AGENTS.md`, and with an adapter, the skills pins in its harness's project settings.

What a consumer must change:

The framework no longer installs the skills, pins a commit or checks which copy loaded: each person installs them the way their harness installs skills, at whatever version that gives, and a session started without them stops and tells the human, as before. Sessions on one ticket may now run different versions of a skill, and a change upstream arrives unannounced; `framework-changes.md` (The skills) lists what the roles rely on, for the steward to read against upstream. This replaces the advice [#124](https://github.com/ajmccall/dual-native/issues/124) added to the pi adapter's README. A consumer changes:
  - **`AGENTS.md`, Skills and roles:** replace the paragraph's sentences about the pinned commit with the template's (`agents-template.md`): the skills are installed the way each person's harness installs skills, and a harness names a skill its own way.
  - **A project with the Claude Code adapter:** run `install --wire <ticket worktree>`, which removes the old pins from `.claude/settings.json`: `extraKnownMarketplaces.dual-native`, and in `enabledPlugins`, `mattpocock-skills@dual-native` and `mattpocock-skills@claude-plugins-official: false`. `install --check` reports each until it's gone.   - **A project with the pi adapter:** run `install --wire <ticket worktree>`, which removes `git:github.com/mattpocock/skills@<commit>` from the `packages` list of `.pi/settings.json`.   - **A project with no adapter:** nothing beyond `AGENTS.md`.
- **An orchestrated builder follows the installed `implement`** ([#128](https://github.com/ajmccall/dual-native/issues/128), part of [#125](https://github.com/ajmccall/dual-native/issues/125)). `orchestrate.md` no longer holds a copy of `implement`'s steps. The orchestrator finds the installed skill's file, as the harness adapter's README says how, and gives each builder its path; the builder reads and follows it, with the builder role's overrides winning, so a builder it starts and one a person starts run the same steps. The Claude Code adapter's README says where the file is, and its pre-flight checks the orchestrator can read it. Builder override 12 now names the self-check's fixed point: the ticket branch, or `main` on a ticket with no platform work. Tried by one subagent on a scratch ticket, not yet on a live one. Nothing to change.

## 6.3.2 (2026-11-21)

An app on 6.3.1 takes this release with `git subtree pull --prefix=framework <framework repository> v6.3.2 --squash` in a take ticket, and these lines are that ticket's acceptance criteria (`framework-changes.md`, Taking a release). It is a patch because no line asks a consumer to change its own files: it narrows the boundary search so a term inside another word no longer fails a commit.

What a consumer must change:

- The pre-commit hook's boundary search counts a boundary term only where it doesn't follow a letter, never inside another word, so a short product name no longer matches an ordinary word that ends in its letters, such as "execute". A term still counts at the start of an identifier, such as `<term>BoardView`, and after a digit, `_` or `-`, but no longer after a letter, as in camelCase `is<term>`. `install` checks a new project's terms the same way, so it no longer refuses a short product name that only appears inside the framework's own words (`hooks/README.md`; [#118](https://github.com/ajmccall/dual-native/issues/118)). Nothing to change.

Projects with hooks of their own must also invoke `framework/hooks/pre-commit` from their pre-merge-commit (unless it already invokes their pre-commit); projects using `framework/hooks/install` need no change. Cherry-picks and rebases still rely on the reviewer’s range check ([#69](https://github.com/ajmccall/dual-native/issues/69)).

## 2.0.0 (2026-10-18)

The first framework release. The lines below are for an app that carried the pre-release framework in its `framework/` folder: it takes the release with `git subtree pull --prefix=framework <framework repository> v2.0.0 --squash` in a ticket with no platform work, and these lines are that ticket's acceptance criteria (`process.md`, Framework changes and releases). A new app has nothing to migrate: it takes the framework with `git subtree add` at this tag and writes its `AGENTS.md` from `agents-template.md`. The lines are grouped in the order a consumer works them.

What a consumer must change:

### Consumer contract

- Write the project's `AGENTS.md` from `agents-template.md`. It now needs a **Human roles** section, a tracker row and a testing reference row in **Where things live**, the fixed **App settings** fields, and a **Deviations** section.
- The human owner is now two roles, the **product owner** and the **framework steward**, which one person may hold. Name both in `AGENTS.md`, and send each decision to the role it belongs to (`process.md`, Human roles).

### Tracker and labels

- Tickets now live in the tracker, not in a tickets folder, and the tracker carries the plan (`tracker.md`, `process.md` Handoffs). Drop the **Plan** and **Tickets** rows from `AGENTS.md`, and add a **Tracker binding** row naming `framework/trackers/github.md` or your own binding. Move each open ticket file into the tracker as a ticket with its platform parts, from the three parts of `ticket-template.md`, keeping the old handoff as its first entry. Turn the plan's unstarted items into ideas, mark the next two or three as next, and move its unresolved choices to the brief's open questions. Closed ticket files and the plan's history can stay as an archive.
- On GitHub, run the label setup in `trackers/github.md`. Relabel `owner:*` labels as `holder:*` (for example `owner:human` as `holder:product-owner` or `holder:framework-steward`), and add the `ticket`, `idea` and `platform:*` kind labels to open issues.
- Ticket branches are now named `<number>-<slug>` after the ticket (`tracker.md`, Ticket name), not `ticket/<file name>`. Review files and evidence folders use the same name.
- Every comment an agent posts on the tracker now starts with a signature line, and an unsigned comment from a human role's handle counts as that role's decision (`tracker.md`, Who writes what). Agents that share a human's account must sign every comment.

### App schema and tickets

- Add an **App schema** row to `AGENTS.md`'s **Where things live**, naming the folder that holds the schema's `README.md` index and one file per feature (`schema-template.md`). The brief now holds only the app's purpose and open questions; the schema holds its behaviour.
- An app that already ships features writes its whole app schema in one adoption ticket before any new feature work (`adoption.md`), and shrinks its brief when that ticket lands. An app with no shipped features starts the schema in its first ticket.
- Tickets now wrap one schema change (`ticket-template.md`). In open tickets, replace **Acceptance criteria** with a **Schema change** section, rename **Decisions needed** to **Decision history**, drop **Constraints and non-goals** (move non-goals into the schema) and move **Implementation notes** into each platform part's **Notes**, adding a **Codebase facts** section there. A ticket with no platform work keeps a **Notes** section in its body.
- In tickets, the **Current owner** field is now **Current holder**, its `human` value is now `product owner` or `framework steward`, and **Owner decisions** is now **Human decisions**, each marked with the role that made it. In Process evidence, **Owner corrections** is now **Corrections**, tagged by human role, and **Decisions sent to the owner** is now **Decisions sent to a human**, per human role. The **Owner parity checklist** is now the **Product owner parity checklist**. Rename them in open tickets.
- Each platform's test seams are agreed while drafting, in its platform part's **Notes**, and approved with the ticket. Add proposed seams to open tickets that aren't approved for build yet. Platform parts gain a **Seams tested** line in their Record.
- The rule that a role path and a ticket are the whole prompt is dropped, with **Prompt additions**. Remove the **Prompt additions** lines from open tickets and platform parts.
- A departure from a convention reference that concerns one feature now goes in that feature's schema file, under **Deliberate platform differences**. Move any such entry out of `AGENTS.md`'s **Deviations**, which keeps only app-wide departures.

### Roles and skills

- Sessions now start with one of Matt Pocock's skills (`github.com/mattpocock/skills`), and each role is laid over its default skills (`process.md`, Skills). Install the skills, run `setup-matt-pocock-skills` once, and keep its block under a new **Agent skills** section in `AGENTS.md`. Add the **Skills and roles** table from `agents-template.md`, and a **Glossary** row to **Where things live**. Where the skills' tracker docs and the tracker binding disagree, the binding wins.
- The coordinator role is removed. A human starts each session and picks the next item from the tracker, and the product owner lands each ticket. Drop any coordinator from the project's docs and prompts. A session asks a human directly when one is in the session, and otherwise posts the question in a handoff entry, with that human role as holder (`process.md`, Asking a human).
- A review's findings are now the `code-review` skill's **Spec** and **Standards** sections, without high, medium or low priorities. A failing criterion or a breach of a convention-reference rule is a **required finding**, which the reviewer hands straight back to the builder; everything else waits for the product owner. Reword any open review that relies on priorities.
- `reviewer-interaction.md` is folded into the reviewer role's **Run the app** section. Repoint the **Testing reference** row and any project doc that names the old file.

### Branches, change requests and acceptance

- The product role now creates the ticket branch when it opens a ticket, so builders no longer create it.
- Each ticket now has change requests (`tracker.md`, Change requests): the product role opens the ticket's change request as a draft at drafting, each builder opens a platform change request into the ticket branch, and the product owner merges the ticket's change request into `main` (`process.md`, Branches and change requests). On GitHub these are pull requests (`trackers/github.md`). Open a draft pull request for each open ticket branch.
- Reviews are posted on the change request they review, as signed comment reviews, and no longer committed. Drop the **Reviews** row from `AGENTS.md`'s **Where things live**; existing review files can stay as history. Review branches are gone.
- Builder evidence moves from the platform part's Record to the platform change request's description (`ticket-template.md`, part 4). Screenshots are attached to it, never committed: delete any `evidence/` folders on open ticket branches, and drop the delete-before-landing step. The platform part's Record keeps **Change request**, **Review**, **Human decisions**, **Decisions discovered during build** and **Process evidence**.
- Screenshots are named after criterion IDs, `<feature>-C<n>` (each convention reference, rule 8.5).
- The parity check is replaced by **acceptance**: the product owner tries either app or both and accepts or returns the build in one answer (`process.md`, Delivery loop step 5). Remove the **Product owner parity checklist** from open tickets. The ticket statuses **ready for parity check** and **approved** are now **ready for acceptance** and **accepted**: relabel open tickets (on GitHub, `status:ready-for-parity-check` to `status:ready-for-acceptance` and the ticket's `status:approved` to `status:accepted`; platform parts keep `status:approved`). In Process evidence, **Parity mismatches** is now **Differences sent to the product owner**.
- A platform fix for **needs changes** goes on the same platform branch and change request; only a platform returned after its change request merged starts a new one. A reviewer squash-merges an approved platform change request into the ticket branch.
- The product role now takes in `main` during the system update, and opens the upstream change request before the ticket lands when the ticket changed `framework/`. The framework steward approves the system update there.
- The product owner may let one platform land first at any time before landing (`process.md`, One platform first).
- A project with separate iOS and Android repositories keeps `framework/` and `AGENTS.md` only in its product repository (`process.md`, Separate platform repositories).
- Taking a framework release is a ticket with no platform work, which the framework steward decides and approves, landed with a merge commit (`process.md`, Framework changes and releases). Any change request that carries a git subtree join or pull lands with a merge commit, not a squash.
- The rule to commit at the start and end of each ticket is dropped.

### Measures

- Measures now live in `measures.md`. Each session's handoff entry ends with a **Cost** line (platform, role, tokens, dollars, agent time), which a harness adapter fills, or "not recorded" without one. Humans no longer log time.
- **Process evidence** is now only in the ticket's Record, and the product role fills it in once, at the start of the system update. Replace it in open tickets with the items in `ticket-template.md`: Cost, Native-twice premium, Corrections, Decisions sent to a human, Review rounds, Required findings, Spec changes after approval, Differences sent to the product owner, Sessions spent on returns and System updates. **Rework** is dropped. Delete **Process evidence** from open platform parts.
- An **app release** is a ticket with platform parts and no schema change, at which builders measure each platform's product outcomes with the new section 10 (Release measures) of each convention reference, and the product role rolls up the tickets since the previous release (`process.md`, App releases). Cold start needs a physical device. At its first app release, a project adds an iOS performance test plan and an Android `:macrobenchmark` module.

### Convention references and dependencies

- In the convention references, the **Owner choice** label is now **Framework choice**. A project that cites the label in its own docs renames it there.
- Dependency policy is now a default in section 9 of each convention reference, not a `process.md` rule: the platform vendor's own frameworks and libraries first (on Android also the Kotlin libraries and JUnit 4), then highly respected third-party libraries with a one-line ticket decision, then hand-written code. The Android closed list is gone. An app may override the default by recording a deviation.
- On Android, the default is now Hilt from the app's first ViewModel (Android rules 9.3 to 9.5, 6.6). A hand-wired Android app either adopts Hilt in a ticket or records hand wiring as a deviation in `AGENTS.md`'s **Deviations**.
- The handoff's dependency listing now covers every package or artifact the build adds compared with `main`, first-tier ones included, each marked first tier or third-party (rule 9.2 of each reference). iOS rules 9.2 and 9.3 are now 9.3 and 9.4; update any citation of them.
- The product owner approves each deviation in the ticket that needs it, and the system update names it (`process.md`, Convention references).
- The convention references no longer require a source for every rule, and an uncited review finding isn't rejected; it just isn't a required finding.
- The saved-data testing rules moved from `process.md` (Builder evidence) into rules 6.7 to 6.10 of each convention reference. A project doc that cites the old paragraph cites those rules instead.

### Pre-commit hook

- The framework ships a pre-commit hook, `framework/hooks/pre-commit`, with four fast checks: whitespace, the app schema's fixed sections and criterion IDs, the shape of each feature's **States**, and the boundary search when `framework/` or `AGENTS.md` changes (`process.md`, Local checks). Run `framework/hooks/install` once in every clone; it sets `core.hooksPath`, and refuses if another hooks path is set, in which case call the framework's hook from your own. Every session runs the install when it starts. It needs the `python3` that Xcode's Command Line Tools provide.
- Add a **Boundary terms** line to `AGENTS.md`'s **App settings**: the app's name and the product words that must never appear in `framework/`. The hook reads it, together with the paths in **Where things live**; a commit that touches `framework/` fails without it. Make sure each path in that table is in backticks, and that the **App schema** row holds the schema folder's path, or the schema check is skipped with a warning.
- A commit made with `--no-verify` needs a human's word and a `Hook-bypassed: <reason>` trailer in its message, and counts as a correction in Process evidence (`measures.md`). No agent bypasses the hook on its own.

### Claude Code adapter

- Add a **Harness adapter** row to `AGENTS.md`'s **Where things live**: the adapter for the harness the team runs, or "None". A session reads the named adapter's README before working (`process.md`, Harness adapters). The adapter pins the skills' version, runs the pre-commit install at session start and prints each session's Cost line; the framework still doesn't require one.
- The first adapter, `framework/adapters/claude-code/`, ships with this release. On Claude Code: name it in `AGENTS.md`, merge its README's block into the project's `.claude/settings.json` (a marketplace that pins `mattpocock-skills`, with the official marketplace's copy switched off, a SessionStart hook and a status line), and each person accepts the workspace trust dialog and runs `claude plugin install mattpocock-skills@dual-native --scope project` once. A project with a `CLAUDE.md` adds the line `@AGENTS.md` to it; one without adds no `CLAUDE.md`.
- With the Claude Code adapter, the Cost line comes from `framework/adapters/claude-code/cost <platform> <role>`, run before the handoff is recorded. Its tokens figure is a lower bound, written `≥ N tokens`, and its agent time is the API time, which leaves out tool runs; both count as recorded (`measures.md`, Cost per session). Anyone with their own Claude Code status line keeps it by moving it to `~/.claude/dual-native-statusline`.
