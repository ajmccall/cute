# Android convention reference

The rules an Android builder follows and an Android reviewer checks against. Cite a rule by its number, for example "rule 4.3". A review finding names the rule behind it where there is one. A breach of a required rule (Required rules, below) is a **required finding**, which the review sends back; a breach of any other rule, which is advisory, is a **nit**, which the builder may take or leave. A finding with no rule behind it still stands, but this reference doesn't make it required. The nine sections match the iOS reference, so "section 4" means navigation on both.

## How to read this reference

- **Assumes** the current stable releases on 2026-10-02:
  - Android 17, API level 37, the latest platform in the stable SDK channel. A platform reaches the stable channel at its Platform Stability milestone: Android 16 was "Released to the stable channel (no longer in preview) when Android 16 reached the Platform Stability milestone" ([SDK Platform release notes](https://developer.android.com/tools/releases/platforms#16)). "Android 17 has officially reached Platform Stability with Beta 3", in March 2026 ([Android 17 release notes](https://developer.android.com/about/versions/17/release-notes#beta3)). `android --no-metrics sdk list --all` lists `platforms/android-37.0` without `--beta` (Android CLI 1.0.16500706). The SDK Platform release notes have no section for Android 17 yet, so don't take the latest level from that page alone.
  - Android Gradle plugin 9.4 ([AGP release notes](https://developer.android.com/build/releases/gradle-plugin)) and Kotlin 2.4 ([Kotlin releases](https://kotlinlang.org/docs/releases.html)).
  - Compose BOM 2026.09.00 ([BOM mapping](https://developer.android.com/develop/ui/compose/bom/bom-mapping)), which maps `androidx.compose.material3` to 1.4.0, its latest stable release ([Material 3 releases](https://developer.android.com/jetpack/androidx/releases/compose-material3#1.4.0)).
  - Navigation 3 1.2.0 ([Navigation 3 releases](https://developer.android.com/jetpack/androidx/releases/navigation3#1.2.0)) and Lifecycle 2.11.0 ([Lifecycle releases](https://developer.android.com/jetpack/androidx/releases/lifecycle#2.11.0)).
  - Checked on 2026-10-18: Hilt (Dagger) 2.60.1 ([Dagger releases](https://github.com/google/dagger/releases)), KSP 2.3.12 ([KSP releases](https://github.com/google/ksp/releases)) and `androidx.hilt` 1.4.0 ([Hilt releases](https://developer.android.com/jetpack/androidx/releases/hilt)).
  - Checked on 2026-11-08: the ktlint Gradle plugin 14.2.0 ([ktlint-gradle releases](https://github.com/JLLeitschuh/ktlint-gradle/releases)) and ktlint 1.8.0 ([ktlint releases](https://github.com/ktlint/ktlint/releases)).

  Update this list, and any rule it affects, when a new stable release lands.
- These rules are guidance. A rule gives its source where that helps: developer.android.com, m3.material.io or kotlinlang.org, or a first-party tool's own help output, for example `adb help`, `android --help`, or a device service's `adb shell cmd <service> help`, cited as the command that prints it, with the tool version or API level it was read on. A new rule needn't have a source, and the sources already given stay. Samples, blogs and source repositories may illustrate a rule.
- Quoted words are copied exactly from the cited page. A rule claims no more than its source says; anything it adds is labelled **Framework choice**.
- Where m3.material.io describes a component or variant that the stable `material3` release doesn't have, the stable library wins (rule 3.2). Where both the M3 guidance and an older option are in the stable release, the rule names the one to use.
- A rule that settles something Google leaves open, or that departs from Google's guidance, is labelled **Framework choice**: a judgement call this reference makes, which a project departs from as the next point says. A rule isn't labelled only because it gives no source. Where Google offers more than one current option, the Framework choice names the alternative, and a project that uses the alternative isn't departing from the rule, so it records no deviation.
- A project never edits this reference. It departs from a required rule, including the section 9 third-party decision, by recording a deviation, which the product owner approves: in `AGENTS.md`'s **Deviations** for the whole app, or in the feature's **Deliberate platform differences** for one feature. Departing from an advisory rule needs no deviation.
- A rule that needs a minimum API level is labelled with it, for example **API 31+**. The project decides its `minSdk`. If that minimum is lower than a rule's label, the builder raises it as a decision rather than working around it. Rules without a label work on every API level that current Compose supports.
- The architecture rules follow Google's [Guide to app architecture](https://developer.android.com/topic/architecture) and its [recommendations](https://developer.android.com/topic/architecture/recommendations).
- `AGENTS.md` holds the rules both platforms share, such as parity and how sessions isolate their work, and they aren't repeated here. Section 9 holds the default dependencies.
- These are rules, not tutorials. Follow the source for detail.

## Required rules

A rule is **required** when a breach harms a person using the app (they can't read, reach or leave something, or they lose saved data), commits the app to something without the product owner, or breaks parallel sessions. Architecture, test method, project setup, look and command-line how-to are advisory. The eight required rules, each labelled **Required** in place:

- 1.9: edge to edge, with content clear of the system bars.
- 2.12, schema export only: Room schemas are exported and committed, so saved data survives an upgrade.
- 4.3: predictive back works, and is never intercepted for business logic.
- 5.2: touch targets of at least 48 × 48 dp.
- 5.3: a `contentDescription` on every meaningful image and icon-only control.
- 5.4: text in `sp`, usable at the largest font scale.
- 8.8: an emulator of its own per session, with `ANDROID_SERIAL` set.
- 9.1, the third-party decision only: no third-party library without the product owner's decision. The preference order itself is advisory.

Every other rule is advisory: a builder follows it by default, and departing from it needs no deviation.

## Design versus platform

- The project's design source, named in `AGENTS.md`, owns the look: colour, type, shape, layout and custom components.
- This reference owns the behaviour that people and the OS rely on: navigation and the back gesture, accessibility (font scaling, TalkBack, touch targets) and system integration such as edge-to-edge.
- When the design really clashes with a rule here, the builder doesn't settle it. It sends the clash to the product owner as a decision in the ticket.

## 1. Project structure

1.1. Build scripts use the Gradle Kotlin DSL (`.gradle.kts`). Source: [Migrate your build configuration from Groovy to Kotlin](https://developer.android.com/build/migrate-to-kotlin-dsl#timeline).

1.2. Every dependency and plugin version lives in the version catalog, `gradle/libs.versions.toml`. Source: [Migrate your build to version catalogs](https://developer.android.com/build/migrate-to-catalogs#create-version).

1.3. Compose libraries take their versions from the Compose BOM, not from individual version numbers. Source: [Use a Bill of Materials](https://developer.android.com/develop/ui/compose/bom#why-bom-recommended).

1.4. Use AGP's built-in Kotlin: don't apply `org.jetbrains.kotlin.android`. Apply the Compose compiler Gradle plugin, `org.jetbrains.kotlin.plugin.compose`. Source: [Migrate to built-in Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin), [Set up the Compose compiler](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler#setup-compose-compiler-version-catalog) (ignore that sample's `org.jetbrains.kotlin.android` line).

1.5. Start with a single `app` module. Split into modules only when a ticket needs it. Source: [Guide to Android app modularization](https://developer.android.com/topic/modularization#is-modularization-for-me), [Common pitfalls](https://developer.android.com/topic/modularization#common-pitfalls) ("It doesn't always make sense to modularize your project").

1.6. The app has a single activity. Screens are composables, not activities. Source: [Architecture recommendations: UI layer](https://developer.android.com/topic/architecture/recommendations#ui-layer) ("Use a single-activity application").

1.7. Inside the module, packages are grouped by feature, with data-layer types in a `data` package. **Framework choice** for the feature grouping; Google only says small apps "can choose to place data layer types in a data package" ([Architecture recommendations: Layered architecture](https://developer.android.com/topic/architecture/recommendations#layered-architecture)).

1.8. `compileSdk` and `targetSdk` are the latest stable API level (see **Assumes**). Google Play requires API 36 or higher for new apps and updates from 31 August 2026. Source: [Configure your build: Android SDK settings](https://developer.android.com/build#android_sdk_settings) ("To use the latest Android features, use the latest Android SDK when compiling"), [Target API level requirements](https://developer.android.com/google/play/requirements/target-sdk).

1.9. **Required.** The app draws edge to edge. Call `enableEdgeToEdge()` in the activity's `onCreate`, and keep content clear of the system bars with insets. Material 3 app bars, `NavigationBar`, `ShortNavigationBar` (rule 4.4) and `NavigationRail` apply their own insets. `Scaffold` doesn't apply insets to its content: it passes them as `innerPadding`, and the content must apply them. Enforced when targeting **API 35+**, with no opt-out from API 36. Source: [Set up edge-to-edge](https://developer.android.com/develop/ui/compose/system/setup-e2e#enable-edge-to-edge), [Window insets](https://developer.android.com/develop/ui/compose/system/insets#inset-fundamentals), [Material components and insets](https://developer.android.com/develop/ui/compose/system/material-insets#inset-handling) (also [#scaffold](https://developer.android.com/develop/ui/compose/system/material-insets#scaffold): "Scaffold does not apply the insets to content; this responsibility is yours"), [ShortNavigationBar](https://developer.android.com/reference/kotlin/androidx/compose/material3/ShortNavigationBar.composable) (`windowInsets: WindowInsets = ShortNavigationBarDefaults.windowInsets`), [Android 16 behaviour changes: Edge-to-edge](https://developer.android.com/about/versions/16/behavior-changes-16#edge-to-edge).

1.10. Kotlin code, including `.gradle.kts` scripts, follows the Android Kotlin style guide and the Kotlin coding conventions. ktlint checks the style guide's mechanical rules, among them "the indent increases by four spaces", "Code has a column limit of 100 characters", and imports "grouped together in a single list and ASCII sorted", so neither the builder nor the reviewer checks those by hand. It applies all of its standard rules in that style, such as wrapping, spacing and trailing commas, not only these three, and its formatting is the project's. Apply the ktlint Gradle plugin, `org.jlleitschuh.gradle.ktlint`, to the `app` module, at 14.1.0 or later, the first release to "Add support for Android projects with new DSL i.e. built-in Kotlin" (rule 1.4). Select ktlint's Android code style in an `.editorconfig` at the root of the Android project:

```ini
[*.{kt,kts}]
ktlint_code_style = android_studio
ktlint_function_naming_ignore_when_annotated_with = Composable
```

The second property keeps the style guide's names for composables: "Functions annotated with @Composable that return Unit are PascalCased". `./gradlew ktlintCheck` "checks all `SourceSet`s and project Kotlin script files", and runs wherever the unit tests run: in the builder's evidence, in the reviewer's reruns, and in the pull request's automated check where the project has one. `./gradlew ktlintFormat` fixes most of what it reports; run it on the files `android create` generates, whose template indents by two spaces, before building on them. The plugin "only activates if that project has the kotlin plugin applied", so the root project's `build.gradle.kts` and `settings.gradle.kts` are outside it: keep them to the same style. Source: [Kotlin style guide](https://developer.android.com/kotlin/style-guide#naming) (also [#indentation](https://developer.android.com/kotlin/style-guide#indentation), [#line_wrapping](https://developer.android.com/kotlin/style-guide#line_wrapping), [#import_statements](https://developer.android.com/kotlin/style-guide#import_statements) and [#function_names](https://developer.android.com/kotlin/style-guide#function_names)), [Coding conventions](https://kotlinlang.org/docs/coding-conventions.html#naming-rules) (also [#indentation](https://kotlinlang.org/docs/coding-conventions.html#indentation): "Use four spaces for indentation"), [ktlint code styles](https://ktlint.github.io/ktlint/latest/rules/code-styles/) ("The `android_studio` (formerly `android`) aims to be compatible with default formatter of Android Studio. This code style is based on Android's Kotlin styleguide"), [ktlint standard rules](https://ktlint.github.io/ktlint/latest/rules/standard/) (for `android_studio`, [#indentation](https://ktlint.github.io/ktlint/latest/rules/standard/#indentation) sets `indent_size` 4 and `indent_style` `space`, [#max-line-length](https://ktlint.github.io/ktlint/latest/rules/standard/#max-line-length) sets `max_line_length` 100, and [#import-ordering](https://ktlint.github.io/ktlint/latest/rules/standard/#import-ordering) sets `ij_kotlin_imports_layout` to `*`, "alphabetical with capital letters before lower case letters"; [#function-naming](https://ktlint.github.io/ktlint/latest/rules/standard/#function-naming): "When using Compose, you might want to configure the `function-naming` rule with `.editorconfig` property `ktlint_function_naming_ignore_when_annotated_with=Composable`"), [ktlint-gradle](https://github.com/JLLeitschuh/ktlint-gradle) (README and [changelog, 14.1.0](https://github.com/JLLeitschuh/ktlint-gradle/blob/main/CHANGELOG.md)). **Framework choice**: ktlint and its Gradle plugin, which Google doesn't name. They run in the build and don't ship in the app, so they aren't a third-party library under rule 9.1 and need no decision.

1.11. User-facing strings live in `res/values/strings.xml` and are read with `stringResource`. Source: [Localize your app: Move all strings into strings.xml](https://developer.android.com/guide/topics/resources/localization#move-strings-xml) ("don't hardcode any strings"), [Resources in Compose: Strings](https://developer.android.com/develop/ui/compose/resources#strings), [String resources](https://developer.android.com/guide/topics/resources/string-resource#String).

1.12. Every dependency is added, or updated, at its latest stable release: for an AndroidX library outside the BOM, the version in the **Stable Release** column of its release page; for any other library, the latest release its own releases page marks stable. Never copy a version from a guide's or sample's setup, which drifts behind the stable releases and may pin alpha ones. A pre-release library is the builder's call, listed in the ticket's pull request. **Framework choice**: Google explains the release stages, including that in alpha "APIs may be added, removed, or changed", but doesn't require stable versions ([AndroidX releases](https://developer.android.com/jetpack/androidx/versions)). The other artifacts that rule 9.1 allows also use stable versions, also as **Framework choice**. The Kotlin serialization plugin takes the project's Kotlin version, as kotlinlang.org's setup does (its Maven example uses `kotlin.version` for the plugin) ([Get started with Kotlin serialization](https://kotlinlang.org/docs/serialization-get-started.html#add-plugins-and-dependencies)). The kotlinx libraries "follow their own versioning, independent of Kotlin" ([Serialization](https://kotlinlang.org/docs/serialization.html#kotlin-serialization-libraries)), so they and JUnit use their latest stable release, not the version in a guide's sample. The standard library needs no version of its own: "The version of the standard library used is the same as the version of the Kotlin Gradle plugin" ([Configure a Gradle project: Dependency on the standard library](https://kotlinlang.org/docs/gradle-configure-project.html#dependency-on-the-standard-library)).

1.13. Use a Media3 API marked `@UnstableApi` only where no stable Media3 API does the job. Opt in with `androidx.annotation.OptIn`, as `@OptIn(UnstableApi::class)`, not with `kotlin.OptIn`, on the class or function that uses it. The ticket's pull request lists each opt-in, with the API that needs it. Opting in this way isn't a deviation. Source: [Media3 troubleshooting: Unstable API lint errors](https://developer.android.com/media/media3/exoplayer/troubleshooting#unstable-api-lint-errors) ("You have two choices to handle unstable API lint errors: Switch to using a stable API that achieves the same result. Continue using the unstable API and annotate the usage with @OptIn"; "It's important to use the androidx.annotation.OptIn annotation"), [UnstableApi](https://developer.android.com/reference/androidx/media3/common/util/UnstableApi) ("It is generally safe for applications to depend on unstable APIs, at the cost of some extra work during upgrades"). **Framework choice**: opting in at the class or function rather than for a whole package or project, which the troubleshooting page also allows, and listing each opt-in in the ticket's pull request.

## 2. Architecture layers and state holders

2.1. The app has a UI layer and a data layer. Add a domain layer only when logic is complex or reused by several ViewModels. Source: [Guide to app architecture: Recommended app architecture](https://developer.android.com/topic/architecture#recommended-app-arch), [Domain layer](https://developer.android.com/topic/architecture/domain-layer) ("The domain layer is an optional layer").

2.2. Data flows one way: state flows down to the UI and events flow up. UI state is immutable. Source: [UI layer: Unidirectional data flow](https://developer.android.com/topic/architecture/ui-layer#udf), [State immutability](https://developer.android.com/topic/architecture/ui-layer#state-immutability).

2.3. Each screen's state holder is a `ViewModel` that exposes its UI state as one `StateFlow<…UiState>` property, `uiState`. It adds more only for unrelated pieces of data, as the source allows. Source: [State holders: ViewModel as state holder](https://developer.android.com/topic/architecture/ui-layer/stateholders#viewmodel-as), [Architecture recommendations: ViewModel](https://developer.android.com/topic/architecture/recommendations#viewmodel).

2.4. Don't send one-off events from the ViewModel to the UI. Model the outcome as state, and have the UI report back when it has handled it. Source: [UI events: Handle ViewModel events](https://developer.android.com/topic/architecture/ui-layer/events#handle-viewmodel-events) ("should always result in a UI state update"; also [#consuming-trigger-updates](https://developer.android.com/topic/architecture/ui-layer/events#consuming-trigger-updates)), [Architecture recommendations: UI layer](https://developer.android.com/topic/architecture/recommendations#ui-layer) ("Do not send events from the ViewModel to the UI").

2.5. The UI collects flows with `collectAsStateWithLifecycle()`. Source: [State and Jetpack Compose: Other types of state](https://developer.android.com/develop/ui/compose/state#use-other-types-of-state-in-jetpack-compose), [Lifecycle-aware flow collection](https://developer.android.com/topic/libraries/architecture/coroutines#lifecycle-aware-flow-collection).

2.6. Only the screen-level composable gets the ViewModel. It passes state and event lambdas to stateless child composables. Don't pass ViewModels down. Source: [State hoisting: Best practice](https://developer.android.com/develop/ui/compose/state-hoisting#best-practice), [ViewModel overview: Best practices](https://developer.android.com/topic/libraries/architecture/viewmodel#best-practices) ("Don't pass ViewModels to other classes, functions or other UI components").

2.7. When a composable has complex UI logic involving the state of its UI elements, that logic lives in a plain state holder class, remembered in composition. Source: [State hoisting: Classes as state owner](https://developer.android.com/develop/ui/compose/state-hoisting#classes-as-state-owner).

2.8. A ViewModel holds no `Context`, `Resources` or view references. Source: [ViewModel overview: Best practices](https://developer.android.com/topic/libraries/architecture/viewmodel#best-practices).

2.9. Repositories are the data layer's entry points. Each piece of data has one repository as its single source of truth. Source: [Data layer: Architecture](https://developer.android.com/topic/architecture/data-layer#architecture), [Source of truth](https://developer.android.com/topic/architecture/data-layer#source-of-truth).

2.10. Async work uses coroutines and flows. ViewModels launch in `viewModelScope`, suspend functions are main-safe, and dispatchers are injected rather than hard-coded. Source: [Coroutines best practices](https://developer.android.com/kotlin/coroutines/coroutines-best-practices#inject-dispatchers) (also [#main-safe](https://developer.android.com/kotlin/coroutines/coroutines-best-practices#main-safe) and [#viewmodel-coroutines](https://developer.android.com/kotlin/coroutines/coroutines-best-practices#viewmodel-coroutines)), [Architecture recommendations: Layered architecture](https://developer.android.com/topic/architecture/recommendations#layered-architecture).

2.11. UI-element state that must survive configuration change and process death uses `rememberSaveable`. Screen state that must survive process death uses `SavedStateHandle`. Source: [Save UI state in Compose](https://developer.android.com/develop/ui/compose/state-saving#ui-logic), [SavedStateHandle APIs](https://developer.android.com/develop/ui/compose/state-saving#savedstatehandle_apis), [Save UI states: Options](https://developer.android.com/topic/libraries/architecture/saving-states#options).

2.12. **Required (schema export).** **Data saved in a Room database.** Use Room 3 (`androidx.room3`). "Room 3.0 requires KSP for annotation processing" ([Save data in a local database using Room: Setup](https://developer.android.com/training/data-storage/room#setup)), and "A `SQLiteDriver` is now required to build a `RoomDatabase`" ([Room 3 releases](https://developer.android.com/jetpack/androidx/releases/room3#3.0.0)). The ticket that adds the database names the driver: `AndroidSQLiteDriver` uses the platform's SQLite, and `BundledSQLiteDriver` adds its own build of SQLite to the app. **Framework choice**. Apply the Room Gradle plugin with `room3 { schemaDirectory("$projectDir/schemas") }`, and commit the schema files it exports: "Store these files in your version control system so that you can recreate lower versions of the database for testing and support automated migration generation" ([Migrate your Room database: Export schemas](https://developer.android.com/training/data-storage/room/migrating-db-versions#export-schemas)). Through `AndroidSQLiteDriver`, a database opens with Android's [DefaultDatabaseErrorHandler](https://developer.android.com/reference/android/database/DefaultDatabaseErrorHandler), which is "used as the default DatabaseErrorHandler" when no handler is given. Its reference doesn't say what it does. On the API 37 emulator, with `androidx.sqlite:sqlite-framework` 2.7.1, opening a main file that wasn't a database deleted it and created a new, empty database in its place. A separate preflight connection using `SQLiteDatabase.openDatabase` with `OPEN_READONLY` and a non-deleting error handler ([SQLiteDatabase](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase)) protects only that inspection, not Room's active connections. For a ticket requiring preservation after opening, choose and verify a non-deleting active driver; preflight alone is insufficient. With `BundledSQLiteDriver` 2.7.1 on API 37, isolated b-tree corruption tests during launch access and runtime returned native error 11 without deleting/replacing the main file or its companions. That is evidence for those tested paths, not every fault. The driver choice, preflight depth and recovery behaviour remain the ticket's decisions. Verify the actual selected driver with isolated connection-level tests and companion-file checks, as rules 6.7 to 6.10 require; fakes or retained UI state cannot prove file preservation. **Framework choice** of the preservation validation; driver API: [BundledSQLiteDriver](https://developer.android.com/reference/kotlin/androidx/sqlite/driver/bundled/BundledSQLiteDriver).

## 3. Building UI

3.1. The design source comes first. If the project names none, the stock component set is Material 3, `androidx.compose.material3`, at its latest stable release through the BOM (rule 1.3). Source: [Material Design 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3#material-theming), [M3 components](https://m3.material.io/components).

3.2. Don't use Material 3 Expressive APIs (anything marked `@ExperimentalMaterial3ExpressiveApi`, or available only in a `1.5.0` alpha) until a stable `material3` release includes them. Source: [Material 3 releases, 1.4.0-beta01](https://developer.android.com/jetpack/androidx/releases/compose-material3#1.4.0-beta01) ("All public APIs tagged with ExperimentalMaterial3ExpressiveApi … have been removed, please switch to 1.5.0-alpha").

3.3. The app has one theme composable that wraps `MaterialTheme` with its colour scheme, typography and shapes. Components read colours, type and shapes from `MaterialTheme`, not from hard-coded values. Source: [Material Design 3 in Compose: Material theming](https://developer.android.com/develop/ui/compose/designsystems/material3#material-theming).

3.4. Not used. The number stays, so the rules after it keep theirs.

3.5. Dynamic colour is a look decision, so the design source makes it. When the design source is standard components, `AGENTS.md` says whether the theme uses dynamic colour where the device supports it (with the project's colour scheme elsewhere), or the static schemes only, the same colours on every device. If it doesn't say, the builder sends it to the product owner as a decision. **API 31+** for dynamic colour. **Framework choice**: Google documents dynamic colour but doesn't require it ([Material Design 3 in Compose: Dynamic color schemes](https://developer.android.com/develop/ui/compose/designsystems/material3#dynamic_color_schemes), [M3: User-generated source](https://m3.material.io/styles/color/dynamic/user-generated-source)).

3.6. **Custom designs.** When the design source is a design system or designs, Google documents three options: extend `MaterialTheme` with extra values, replace one or more Material subsystems, or build a fully custom design system on Compose Foundation. This reference doesn't choose. The ticket that introduces the design source sends the choice to the product owner. Source: [Custom design systems in Compose](https://developer.android.com/develop/ui/compose/designsystems/custom#extending-material) (also [#replacing-systems](https://developer.android.com/develop/ui/compose/designsystems/custom#replacing-systems) and [#implementing-fully-custom](https://developer.android.com/develop/ui/compose/designsystems/custom#implementing-fully-custom)), [Anatomy of a theme](https://developer.android.com/develop/ui/compose/designsystems/anatomy#system-composition-locals).

3.7. **Design tokens.** The design source's tokens (colour, type, shape, spacing) map to theme values in one place, and components read them from the theme. Tokens that the theme doesn't carry are provided through a `CompositionLocal`. Use `CompositionLocal` only for tree-wide values like these, not to pass ordinary data. Source: [M3: Design tokens](https://m3.material.io/foundations/design-tokens/overview), [Locally scoped data with CompositionLocal: Deciding whether to use CompositionLocal](https://developer.android.com/develop/ui/compose/compositionlocal#deciding).

3.8. **Custom components.** A reusable composable accepts `modifier: Modifier = Modifier` and applies it to its root. It takes content through slot parameters (composable lambdas) where callers need to vary it, and is stateless: it takes a value and an `on…Change` lambda. Source: [Compose modifiers](https://developer.android.com/develop/ui/compose/modifiers) ("best practice to have all of your composables accept a modifier parameter"), [Compose layout basics: Slot-based layouts](https://developer.android.com/develop/ui/compose/layouts/basics#slot-based-layouts), [State and Jetpack Compose: State hoisting](https://developer.android.com/develop/ui/compose/state#state-hoisting) (`value: T` and `onValueChange: (T) -> Unit`), [State hoisting: Best practice](https://developer.android.com/develop/ui/compose/state-hoisting#best-practice). Google's [API guidelines page](https://developer.android.com/develop/ui/compose/api-guidelines) links to the full component guidelines, which are kept in the AndroidX source repository; they illustrate this rule.

3.9. Every custom component meets section 5 itself: semantics, a 48 dp touch target and font scaling. Source: [Accessibility API defaults: Custom components](https://developer.android.com/develop/ui/compose/accessibility/api-defaults#custom-components).

3.10. Each screen and reusable component has a `@Preview`. **Framework choice** to require them; the API is at [Preview your UI with composable previews](https://developer.android.com/develop/ui/compose/tooling/previews#preview-definitions) (dark: [#ui-mode](https://developer.android.com/develop/ui/compose/tooling/previews#ui-mode)).

## 4. Navigation and back behaviour

4.1. Navigate with Navigation 3 (`androidx.navigation3`). The back stack is state the app owns: keys implement `NavKey` and are `@Serializable`, the stack is created with `rememberNavBackStack`, and `NavDisplay` shows it. **Framework choice** between Google's two navigation libraries. Google's recommendations name Navigation 3 ([Architecture recommendations: UI layer](https://developer.android.com/topic/architecture/recommendations#ui-layer); [Navigation 3](https://developer.android.com/guide/navigation/navigation-3), [Get started](https://developer.android.com/guide/navigation/navigation-3/get-started#project-setup), [Save and manage navigation state](https://developer.android.com/guide/navigation/navigation-3/save-state#use-remembernavbackstack)). Alternative: Navigation Compose 2.x (`androidx.navigation`) with type-safe routes ([Type safety](https://developer.android.com/guide/navigation/design/type-safety#routes)), whose [release page](https://developer.android.com/jetpack/androidx/releases/navigation) now says the library is in maintenance mode.

4.2. The app has a fixed start destination, and the back stack is the navigation state. Up and Back behave the same inside the app, and Up never leaves it. Source: [Principles of navigation](https://developer.android.com/guide/navigation/principles#fixed_start_destination) (also [#navigation_state_is_represented_as_a_stack_of_destinations](https://developer.android.com/guide/navigation/principles#navigation_state_is_represented_as_a_stack_of_destinations) and [#up_and_back_are_identical_within_your_apps_task](https://developer.android.com/guide/navigation/principles#up_and_back_are_identical_within_your_apps_task)).

4.3. **Required.** Keep predictive back working: it is on by default when targeting **API 36+**, so don't opt out. Intercept back only to dismiss UI the person opened (for example, a sheet or an edit in progress), with `BackHandler` or `PredictiveBackHandler`. Never intercept it to run business logic or to log. Source: [Android 16 behaviour changes: Predictive back](https://developer.android.com/about/versions/16/behavior-changes-16#predictive-back), [Add support for the predictive back gesture](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#ui-logic) ("Don't create these callbacks to run business logic or to log"; also [#compose-back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#compose-back) and [#opt-out](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#opt-out)).

4.4. Three to five top-level destinations of equal importance use a navigation bar. Source: [M3: Navigation bar](https://m3.material.io/components/navigation-bar/overview) ("Can contain 3-5 destinations of equal importance"). **Framework choice** of component, because Google's pages differ: use `ShortNavigationBar` with `ShortNavigationBarItem`, the flexible bar that the M3 page now recommends ("Baseline navigation bar is no longer recommended"), stable from `material3` 1.4.0 ([ShortNavigationBar](https://developer.android.com/reference/kotlin/androidx/compose/material3/ShortNavigationBar.composable)). Alternative: `NavigationBar`, the baseline bar that the [Compose navigation bar guide](https://developer.android.com/develop/ui/compose/components/navigation-bar) still shows. Where the app must adapt to larger windows, use the `NavigationSuiteScaffold` overload that takes `navigationItems`, whose default `navigationSuiteType` returns "the recommended NavigationSuiteType … following the Material specifications" for the window ([NavigationSuiteScaffold](https://developer.android.com/reference/kotlin/androidx/compose/material3/adaptive/navigationsuite/NavigationSuiteScaffold.composable), [NavigationSuiteScaffoldDefaults](https://developer.android.com/reference/kotlin/androidx/compose/material3/adaptive/navigationsuite/NavigationSuiteScaffoldDefaults); the older overload in [Build adaptive navigation](https://developer.android.com/develop/ui/compose/layouts/adaptive/build-adaptive-navigation#create_a_scaffold) shows the baseline bar).

4.5. Each screen's `ViewModel` is scoped to its Navigation 3 entry, so it is cleared when the screen leaves the back stack. Add `rememberSaveableStateHolderNavEntryDecorator()` and then `rememberViewModelStoreNavEntryDecorator()`, from `androidx.lifecycle:lifecycle-viewmodel-navigation3`, to the `NavDisplay`'s `entryDecorators`. Without the ViewModel decorator, a `ViewModel` is scoped to the nearest `ViewModelStoreOwner`, typically the activity. Take the artifact's version from the **Stable Release** column of the Lifecycle release page (rule 1.12), not from the Navigation 3 setup sample, which pins an alpha. Source: [Save and manage navigation state: Scoping ViewModel instances to NavEntry objects](https://developer.android.com/guide/navigation/navigation-3/save-state#scoping-viewmodels), [Lifecycle releases](https://developer.android.com/jetpack/androidx/releases/lifecycle#2.11.0).

## 5. Accessibility

5.1. Follow Google's accessibility basics for every screen. Material and Foundation components supply most semantics by default; custom ones must add them (rule 3.9). Source: [Make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/apps), [Accessibility in Compose](https://developer.android.com/develop/ui/compose/accessibility), [Accessibility API defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults).

5.2. **Required.** Every touch target is at least 48 × 48 dp. Source: [Accessibility API defaults: Minimum target sizes](https://developer.android.com/develop/ui/compose/accessibility/api-defaults#minimum-target-sizes), [Make apps more accessible: Large controls](https://developer.android.com/guide/topics/ui/accessibility/apps#large-controls), [M3: Structure](https://m3.material.io/foundations/designing/structure).

5.3. **Required.** Every meaningful image and icon-only control has a `contentDescription`; decorative ones pass `null`. Related elements are merged with `semantics(mergeDescendants = true)`, and custom controls set a `Role`. Source: [Make apps more accessible: Describe each UI element](https://developer.android.com/guide/topics/ui/accessibility/apps#describe-ui-element), [Merging and clearing](https://developer.android.com/develop/ui/compose/accessibility/merging-clearing#merge-semantics), [Semantics: Properties](https://developer.android.com/develop/ui/compose/accessibility/semantics#properties).

5.4. **Required.** Text sizes are in `sp`, and every screen stays usable at the largest font scale (200% from **API 34**). Source: [Android 14 features: Non-linear font scaling](https://developer.android.com/about/versions/14/features#non-linear-font-scaling) (also [#sp-units](https://developer.android.com/about/versions/14/features#sp-units)).

5.5. Text contrast is at least 4.5:1 for text under 18 sp (or bold text under 14 sp), and at least 3:1 for other text. Source: [Make apps more accessible: Text visibility](https://developer.android.com/guide/topics/ui/accessibility/apps#text-visibility), [M3: Color contrast](https://m3.material.io/foundations/designing/color-contrast).

5.6. Check each new screen with TalkBack and Accessibility Scanner. Once a flow has Compose UI tests, they call `enableAccessibilityChecks()`. **Framework choice** to require these; the tools are at [Test your app's accessibility](https://developer.android.com/guide/topics/ui/accessibility/testing#talkback) (also [#accessibility-scanner](https://developer.android.com/guide/topics/ui/accessibility/testing#accessibility-scanner)) and [Accessibility testing in Compose](https://developer.android.com/develop/ui/compose/accessibility/testing#checks). On the emulator, turn TalkBack on with `adb shell settings put secure enabled_accessibility_services com.google.android.marvin.talkback/.TalkBackService`, and off again with `adb shell settings delete secure enabled_accessibility_services`. Source: [Settings.Secure: ENABLED_ACCESSIBILITY_SERVICES](https://developer.android.com/reference/android/provider/Settings.Secure#ENABLED_ACCESSIBILITY_SERVICES) ("List of the enabled accessibility providers"), `adb shell settings help` (`put`, `delete`), and `adb shell pm query-services --components -a android.accessibilityservice.AccessibilityService`, which prints TalkBack's component (API 37 emulator). **Framework choice** of the command line. Alternative: Settings > Accessibility > TalkBack ([#turn-on-talkback](https://developer.android.com/guide/topics/ui/accessibility/testing#turn-on-talkback)). From the command line, a screenshot shows where TalkBack's focus is, but not what it says, so a person listening with TalkBack on is the check of its speech.

## 6. Unit testing

6.1. Unit tests are local tests in `src/test`, run on the JVM with JUnit 4. Source: [Build local unit tests](https://developer.android.com/training/testing/local-tests#location) (also [#dependencies](https://developer.android.com/training/testing/local-tests#dependencies)), [Fundamentals of testing: Instrumented versus local tests](https://developer.android.com/training/testing/fundamentals#instrumented-vs-local). Logic that local tests cover uses Kotlin and Java APIs, not Android framework classes such as `android.icu` or `android.util.Xml`: in local tests, the Android framework's methods have no code, and "if any of the methods are accessed, the test throws an exception" ([Build local unit tests: Mockable Android library](https://developer.android.com/training/testing/local-tests#mockable-library)). Where the JVM's version of an API can behave differently from the device's, the ticket's pull request says so.

6.2. Unit tests cover ViewModels (including their flows) and the data layer. Source: [What to test: Essential](https://developer.android.com/training/testing/fundamentals/what-to-test#essential), [Architecture recommendations: Testing](https://developer.android.com/topic/architecture/recommendations#testing).

6.3. Tests use fakes, not mocks: hand-written classes that implement the same interface as the real dependency. Source: [Test doubles: Types](https://developer.android.com/training/testing/fundamentals/test-doubles#types) ("Fakes … are preferred"), [Architecture recommendations: Testing](https://developer.android.com/topic/architecture/recommendations#testing). Local tests construct ViewModels and other injected classes directly with their fakes, without Hilt (rule 9.3): "Hilt isn't necessary for unit tests, since when testing a class that uses constructor injection, you don't need to use Hilt to instantiate that class", and "In unit tests, construct the ViewModel directly with fakes" ([Hilt testing guide](https://developer.android.com/training/dependency-injection/hilt-testing)).

6.4. Coroutine code is tested with `runTest` from `kotlinx-coroutines-test`, with injected test dispatchers, and `Dispatchers.setMain` for code that uses the main dispatcher. Source: [Testing Kotlin coroutines on Android](https://developer.android.com/kotlin/coroutines/test#invoking-suspending-functions) (also [#standardtestdispatcher](https://developer.android.com/kotlin/coroutines/test#standardtestdispatcher) and [#setting-main-dispatcher](https://developer.android.com/kotlin/coroutines/test#setting-main-dispatcher)), [kotlinx-coroutines-test](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-test/).

6.5. Code that needs the Android framework itself, such as a Room database on the platform's SQLite (rule 2.12), is tested with instrumented tests, which run on the emulator. Everything local tests can reach stays in local tests (rule 6.1). Instrumented tests live in `src/androidTest`, run with `testInstrumentationRunner = "androidx.test.runner.AndroidJUnitRunner"` (or, once a test needs Hilt, the runner in rule 6.6), and use `@RunWith(AndroidJUnit4::class)`, as Google's Room sample does. Run them with `./gradlew connectedDebugAndroidTest`, with `ANDROID_SERIAL` set to the session's own emulator (rule 8.8), and record the device and its API level in the ticket's pull request. Source: [Build instrumented tests: Set up your testing environment](https://developer.android.com/training/testing/instrumented-tests#set-testing), [Test and debug your database: Test on a device that runs Android](https://developer.android.com/training/data-storage/room/testing-db#android) ("we recommend that you write a JUnit test that runs on a device that runs Android"), [Test from the command line: Run tests with Gradle](https://developer.android.com/studio/test/command-line#run-tests-with-gradle) (`connectedAndroidTest`, and `connectedVariantNameAndroidTest` for one variant). The tests run with the app's own `Application` subclass: `ApplicationProvider.getApplicationContext()` "returns your custom subclass's context" ([AndroidJUnitRunner: Access the application's context](https://developer.android.com/training/testing/instrumented-tests/androidx-test-libraries/runner#access-context)). With rule 6.6's runner, `HiltTestApplication` takes its place. Either way, whatever runs at launch in that `Application`, or in an activity a test starts, such as opening the app's saved data, also happens during the tests. The ticket's pull request says how the tests keep away from the app's real data. **Framework choice**. On the API 37 emulator, the task uninstalls the app when it ends, which deletes the app's data, so take screenshots after it, not before. It does so on every device it runs on, which is why rule 8.8 sets the serial. Twice it reported "No compatible devices connected" while `adb devices` listed the emulator, and a second run passed.

6.6. An instrumented test that needs objects from the Hilt graph, such as a UI test of a screen whose ViewModel uses `hiltViewModel()`, is annotated `@HiltAndroidTest` and adds `HiltAndroidRule(this)` as its first rule (`@get:Rule(order = 0)`). The module's instrumented tests run with a custom runner that subclasses `AndroidJUnitRunner` and returns `HiltTestApplication` from `newApplication`. A test replaces a binding with a fake through a module in `src/androidTest` annotated `@TestInstallIn(components = [...], replaces = [...])`, which applies to every test there; use `@UninstallModules` only for one test's replacement. Add `com.google.dagger:hilt-android-testing` with `kspAndroidTest` for the compiler. A test that constructs its objects itself, such as a store test on a real database, doesn't need Hilt. Source: [Hilt testing guide](https://developer.android.com/training/dependency-injection/hilt-testing) ("You must execute instrumented tests that use Hilt in an `Application` object that supports Hilt"; "The recommendation is to use `@TestInstallIn` whenever possible").

6.7. **When a ticket changes saved data.** Rules 6.8 to 6.10 apply to a ticket that adds or changes a write to saved data, or changes what the app does with a damaged store. They are instrumented tests (rule 6.5) on the real Room database, opened through the driver the app uses (rule 2.12), each in its own new folder. A fake store, including one that holds a write until the test releases it, and state the UI kept can't show what reached the disk, so neither is evidence for these rules. **Framework choice**, from reviews where fakes passed and the database disagreed.

6.8. **A write that can be cancelled** (for example when leaving a screen clears its ViewModel while the write runs) is tested cancelled at two points: after its statements but before the transaction commits, and just after the commit. Wrap the real `SQLiteDriver` in a test driver that runs a hook after a chosen statement, such as the mutation or `END TRANSACTION`, and cancel the caller's job there. After each, compare what the repository holds, and what the screen state shows, with what the database holds, asserting every field the write saves, including a field a ticket adds to an existing write. Then close and reopen the store and compare again. A coroutine cancelled after the commit still gets a `CancellationException` when `withContext` returns: if the caller's context "is cancelled by the time its dispatcher starts to execute the code, it discards the result of withContext and throws a CancellationException" ([withContext](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/with-context.html)). So code that updates a cache only after the write returns must not lose that update. **Framework choice**.

6.9. **Keeping files when damage is found.** Where a ticket requires the store's files to be kept rather than deleted, reset or replaced, show it on the driver the app actually opens, at each point the ticket names, such as at launch and while running. Damage a page of the real database file, run the access, and compare the main file and each companion file (`-wal`, `-shm`, `-journal`) before and after, by bytes and inode. The `-shm` file's reader bookkeeping may change, and an assertion allows for it. Rule 2.12 says what the platform's default error handler does. **Framework choice**.

6.10. **Damage fixtures.** A test that injects damage seeds the database through the real store, closes it and lets the close finish, then writes the damage, so no later checkpoint or teardown from the seed overwrites it. It then checks the damaged bytes are on disk before the access under test. A helper that several tests share for writing the damage makes that check itself, so no test that uses it can leave it out. **Framework choice**.

6.11. **Playback from outside the app.** A criterion about playback that a person can also drive from the system's media controls, such as the notification, the lock screen or a headset, is tested through a second `MediaController` connected to the app's session, as well as through the app's own UI, in each state of playback that the criterion names, such as playing, paused and failed. Source: [Connect to a media app](https://developer.android.com/media/media3/session/connect-to-media-app). **Framework choice**, from reviews where a seek sent from the system controls while playback had failed took a path that no test drove.

## 7. Command-line build

7.1. Gradle runs on Android Studio's bundled JetBrains Runtime (on macOS, `/Applications/Android Studio.app/Contents/jbr/Contents/Home`). For a terminal build, set `JAVA_HOME` to it, and set Android Studio's Gradle JDK to the same JDK. Google documents that a terminal build uses `JAVA_HOME` and recommends matching the two ([Java versions in Android builds](https://developer.android.com/build/jdks#jdk-gradle)). Other settings can choose a different JDK for the daemon: `org.gradle.java.home` in a `gradle.properties` file, and Gradle Daemon JVM criteria, which Android Studio uses by default for new projects ([#jdk-config-in-studio](https://developer.android.com/build/jdks#jdk-config-in-studio)). Check which JDK the daemon used with rule 7.5. **Framework choice** of the JBR, and of how the project makes sure the daemon uses it, for example by not using Daemon JVM criteria, or by setting criteria that select it. The ticket that sets up the app decides, and the project's `AGENTS.md` records the choice. If criteria select the JBR and the build fails with "Unable to download toolchain matching the requirements", Gradle hasn't found the JBR: list its path in `org.gradle.java.installations.paths` in the project's `gradle.properties`. That path is machine-specific, so `AGENTS.md` records it under App settings. **Framework choice**. Context: Gradle's documentation, which Google's page links to, says criteria choose among the JDKs that Gradle auto-detects or downloads ([Gradle Daemon: Auto-detection and auto-provisioning](https://docs.gradle.org/current/userguide/gradle_daemon.html#sec:detect_provision)), and that `org.gradle.java.installations.paths` adds JDKs to detection ([Toolchains: Custom toolchain locations](https://docs.gradle.org/current/userguide/toolchains.html#sec:custom_loc)).

7.2. Always use the project's Gradle wrapper, `./gradlew`. Build with `./gradlew assembleDebug`. Source: [Build your app from the command line](https://developer.android.com/build/building-cmdline#DebugMode).

7.3. Run unit tests with `./gradlew testDebugUnitTest` (or `./gradlew test` for every variant). Source: [Test from the command line](https://developer.android.com/studio/test/command-line#run-tests-with-gradle). A reviewer's rerun adds `--rerun-tasks`, so that Gradle's build cache can't stand in for a run, and the review names it. Source: [Profile your build](https://developer.android.com/build/profile-your-build#gradle-profile-option) ("`--rerun-tasks`: Forces Gradle to rerun all tasks and ignore any task optimizations").

7.4. Run `./gradlew lint`, and report any new warnings in the ticket's pull request. **Framework choice** to require it; the task is at [Improve your code with lint checks: Run lint from the command line](https://developer.android.com/studio/write/lint#commandline).

7.5. Record the output of `./gradlew --version` in the ticket's pull request, including its `Daemon JVM` line, which names the JDK that ran the build and the setting it came from. A reviewer then knows which toolchain built it. **Framework choice**.

7.6. The build specifies its Java toolchain version, so the JDK that compiles the code and runs unit tests doesn't depend on the machine. The ticket that sets up the app chooses the version. Source: [Java versions in Android builds: Which JDK compiles my Java source code?](https://developer.android.com/build/jdks#toolchain) ("We recommend that you always specify the Java toolchain").

7.7. Evidence from a test run names how many tests ran. `connectedDebugAndroidTest` can exit 0 having run none, for example after `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, so read the count from its XML results under `build/outputs/androidTest-results/connected/`, and count a run of zero tests as a failure. A comma-separated list of classes in `-Pandroid.testInstrumentationRunnerArguments.class` has run only its first class, so check the count against the tests the run names. **Framework choice**, from sessions where both passed unnoticed.

## 8. Command-line emulator screenshots

8.1. Create the emulator's AVD with the Android CLI, `android emulator create`, and start a session's own instance of it as rule 8.8 says. `android emulator start <device>` can't choose a port or start the AVD read-only (`android emulator start --help`, Android CLI 1.0.16500706), so a session doesn't start a shared AVD with it. `android emulator create` takes only a device profile (`android emulator create --help`, Android CLI 1.0.16500706), and it fails if an AVD folder with the name it chooses already exists ("…avd already exists"), even one whose name differs only in case. Don't remove or change an existing AVD to get round this: reuse it if it runs the API level the ticket needs (`android emulator list`), or else send it to the product owner (**Framework choice**). The Android CLI is also a **Framework choice**: Google now marks `avdmanager`, `sdkmanager` and the `emulator` command-line tool as deprecated in favour of the Android CLI ([avdmanager](https://developer.android.com/tools/avdmanager), [sdkmanager](https://developer.android.com/tools/sdkmanager), [Start the emulator from the command line](https://developer.android.com/studio/run/emulator-commandline); [Android CLI](https://developer.android.com/tools/agents/android-cli), [android emulator](https://developer.android.com/tools/agents/android-cli/commands/emulator)). Alternative: the deprecated tools, which still ship with the SDK, although cmdline-tools 12.0's `avdmanager` can't read an API 37 system image ("unexpected element … abis"). Every `android` command passes `--no-metrics`, so the CLI collects no usage data. **Framework choice**; the flag is at [Android CLI: Data collected](https://developer.android.com/tools/agents/android-cli#data-collected) ("To disable data collection, use the --no-metrics flag when running a command with Android CLI").

8.2. Build with `./gradlew assembleDebug`, install with `adb install -r <apk>` and launch with `adb shell am start -W -n <package>/<activity>`, with `ANDROID_SERIAL` set (rule 8.8). `./gradlew installDebug` gives no way to choose the device (`./gradlew help --task installDebug`, AGP 9.4.1), so a session doesn't use it. **Framework choice**; `-r` is in `adb help` ("replace existing application"; adb 36.0.0). Before a screenshot, check that the `Activity:` line that `-W` prints names the app's own activity. Just after an install on API 37, a system "Updating..." screen can cover the app; if it does, run `adb shell am force-stop <package>` and launch again. **Framework choice** to check; `-W` is in `adb shell am help` ("wait for launch to complete"; API 37 emulator). Source: [Build your app from the command line: Deploy to the emulator](https://developer.android.com/build/building-cmdline#RunningOnEmulator), [Android Debug Bridge: Activity manager](https://developer.android.com/tools/adb#am) (also [#IntentSpec](https://developer.android.com/tools/adb#IntentSpec)).

8.3. Take each screenshot with `adb exec-out screencap -p > <file>.png`. Source: [Android Debug Bridge: Take a screenshot](https://developer.android.com/tools/adb#screencap). Alternative: [`android screen capture`](https://developer.android.com/tools/agents/android-cli/commands/screen_capture), with `--no-metrics` (rule 8.1).

8.4. When a criterion needs dark theme or a large font scale, set them with `adb shell cmd uimode night yes` and `adb shell settings put system font_scale <scale>`. Source: `adb shell cmd uimode help` (`night [yes|no|auto|…]`) and `adb shell settings help` (`put … NAMESPACE KEY VALUE`), read on an API 36 emulator. Google documents the `font_scale` key only for TV ([Accessibility on TV: Text scaling](https://developer.android.com/training/tv/accessibility#text-scaling)), so using it on a phone is a **Framework choice**. Alternative: change them in the emulator's Settings.

8.5. Name each screenshot after the ID of the acceptance criterion it shows, as `<feature>-C<n>`, save it in `~/Library/Caches/<repository>/evidence/<ticket number>-<platform>/`, and give that folder's path in the ticket's pull request with each file listed under its criterion. `gh` can't attach an image, and a session's own temporary folder doesn't outlive it. Never commit it. One screenshot can show several criteria: name it after all of them, for example `saved-items-C1-C2.png`. For a criterion of a ticket that changes no app behaviour, which has no ID, use a short name for the criterion. **Framework choice**.

8.6. When a criterion needs a screenshot of something off screen at launch, such as the end of a long list, scroll with `adb shell input swipe <x1> <y1> <x2> <y2> [duration(ms)]`, dragging from low on the screen to high, and repeat until the element is in view before the screenshot. When it needs taps or typing, such as an open dialog or text in a field, tap with `adb shell input tap <x> <y>` and type with `adb shell input text <string>`, taking each element's coordinates from its `bounds` in `adb shell uiautomator dump`, which writes the screen's UI hierarchy to `/sdcard/window_dump.xml`. Before tapping a button that submits typed text, dump again and check that the field holds all of it: a system dialog that opens meanwhile can take some of the input. Source: `adb shell input` help (`swipe <x1> <y1> <x2> <y2> [duration(ms)] (Default: touchscreen)`, `tap <x> <y> (Default: touchscreen)`, `text <string> (Default: keyboard)`) and `adb shell uiautomator` help (`dump: creates an XML dump of current UI hierarchy`; API 37 emulator). `uiautomator dump` waits for the screen to go idle, so it fails ("could not get idle state") while something animates without end, such as an indeterminate progress indicator. Then take the coordinates from a screenshot instead, and check the field's text in a screenshot before tapping the button. **Framework choice**.

8.7. For stable review flows, maintain native AndroidX UI tests; choose UI Automator when the check crosses between the app and system UI. Assert the action's result with bounded element waits. Every session runs on its own emulator (rule 8.8); use `adb -s <serial>` or `ANDROID_SERIAL`, and each Android CLI command's explicit device selector, for installation, input, inspection and cleanup. Source: [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator), [Android Debug Bridge: Send commands to a specific device](https://developer.android.com/tools/adb#directingcommands). **Framework choice** of maintained native checks and isolated reviewer sessions.

8.8. **Required.** Every session that reaches a device, whatever its role, runs on an emulator of its own, which no other session uses, and sets `ANDROID_SERIAL` to its serial, `emulator-<port>`, for every Gradle and `adb` command that reaches a device. A command that reads only the host, such as `adb version` or `./gradlew --version`, doesn't need it. Every session sets it, because one without it reaches every device: `connectedDebugAndroidTest` runs on every connected device and uninstalls the app when it ends (rule 6.5), deleting another session's app and data mid-run. `adb` reads the variable: "you can set the `$ANDROID_SERIAL` environment variable to contain the serial number instead"; without it, a command fails when two devices run: "adb: more than one device/emulator" ([Send commands to a specific device](https://developer.android.com/tools/adb#directingcommands)). The connected test task "Installs and runs the tests for debug on connected devices", and reads the variable too: its `--serial` option "will take precedence over the serials specified in the ANDROID_SERIAL environment variable" (`./gradlew help --task connectedDebugAndroidTest`, AGP 9.4.1).

- **Start.** Every session, a reviewer's included, starts its emulator when it adds its worktree, as a read-only instance of an existing AVD that runs the API level the ticket needs (rule 8.1): `emulator -avd <AVD> -read-only -port <port>`, adding `-no-window` when no one needs to see it. `-read-only` is to "allow running multiple instances of emulators on the same AVD, but cannot save snapshot" (`emulator -help`, emulator 37.2.12). Choose an even port from 5556 to 5584 that is free, with the port after it. A port that `adb devices` lists isn't free; a test that binds both ports on `127.0.0.1` also finds an emulator that `adb` hasn't attached, and meets this rule. The emulator's own limit is `<port> must be an *even* integer between 5554 and 5584 included. <port>+1 must also be free and will be reserved for ADB` (`emulator -help-port`, emulator 37.2.12). Leave `-gpu` at its default or pass `-gpu host`: an instance started with `-gpu swiftshader_indirect` crashed partway through an instrumented run on one Mac, and the rerun with `-gpu host` passed.
- **Every instance read-only.** A read-only instance doesn't start while the same AVD runs without the flag: "Another emulator instance is running. Please close it or run all emulators with -read-only flag" (emulator 37.2.12). So everyone, sessions and people, starts a shared AVD with `-read-only`, never with `android emulator start` (rule 8.1). Never stop or wipe an instance another session or a person started.
- **Check it's yours.** When `adb -s emulator-<port> shell getprop sys.boot_completed` prints `1`, check that `adb -s emulator-<port> emu avd name` prints the AVD you started, before any other command. An instance started on a port another emulator already held still booted, and its serial reached the other emulator (emulator 37.2.12). If the name differs, stop your own instance by its process and choose another port. The console command `avd name` "Queries the virtual device name" ([Send emulator console commands: General commands](https://developer.android.com/studio/run/emulator-console)).
- **Stop.** Stop it with `adb -s emulator-<port> emu kill` when the session removes its worktree. `kill` "Terminates the virtual device" (same page). Leave Gradle daemons to expire: `./gradlew --stop` stops every session's daemons of that Gradle version, ending their builds and test runs. **Framework choice**, from a review whose `--stop` at cleanup reached another session.

**Framework choice** of one emulator per session, and of read-only instances, which need the SDK's `emulator` command although Google marks it deprecated (rule 8.1), because the Android CLI can't choose a port or read-only mode. Alternative: an AVD of the session's own in a new `ANDROID_AVD_HOME`, with `ANDROID_USER_HOME` beside it; but `android emulator create` there chose its own system image, downloading API 36.1 into the SDK, and can't name the AVD or choose its API level (Android CLI 1.0.16500706).

## 9. Dependencies

This section is this reference's default. An app may override any of it by recording a deviation (How to read this reference).

9.1. **Required (third-party decision).** **Preference order.** Build on these, in order:

1. **Google's own libraries**: AndroidX/Jetpack and any other library Google publishes officially, such as Hilt (rule 9.3), plus the Kotlin libraries JetBrains publishes (the standard library, coroutines and flows, serialization, and `kotlinx-coroutines-test`) and JUnit 4 for local tests. These need no decision.
2. **A highly respected third-party library**, widely used, actively maintained and stable, where the first tier doesn't offer what a ticket needs. It needs a one-line decision in the ticket, naming the library and what its documentation says it brings, which the product owner approves with the ticket.
3. **Hand-written code**, where neither does.

Custom design-system components are expected; the order governs what they are built on. **Framework choice**. Context: [Kotlin coroutines on Android](https://developer.android.com/kotlin/coroutines) ("Coroutines is our recommended solution"), [Build local unit tests: Dependencies](https://developer.android.com/training/testing/local-tests#dependencies), [Navigation 3: Get started](https://developer.android.com/guide/navigation/navigation-3/get-started#project-setup) (Kotlin serialization for navigation keys).

9.2. **Dependency listing.** The ticket's pull request lists every artifact the build adds, including those a library brings with it, from `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` compared with the same report on `main`. It marks each one first tier or third-party, so the product owner can confirm any that no decision named, or query a first-tier one. **Framework choice**; for the report: [Viewing dependencies: Specifying a dependency configuration](https://docs.gradle.org/current/userguide/viewing_debugging_dependencies.html#sec:specifying_a_dependency_configuration).

9.3. **Hilt, from the first ViewModel.** Dependencies are injected with Hilt from the app's first ViewModel. Apply the Hilt Gradle plugin, `com.google.dagger.hilt.android`, and KSP, `com.google.devtools.ksp`, which Room already needs (rule 2.12), and add `com.google.dagger:hilt-android` with `ksp("com.google.dagger:hilt-compiler")`. Use KSP, not kapt: "The `org.jetbrains.kotlin.kapt` (or `kotlin-kapt`) plugin is incompatible with built-in Kotlin" ([Migrate to built-in Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin)), which rule 1.4 uses. Annotate the `Application` subclass `@HiltAndroidApp` and the activity `@AndroidEntryPoint`. Take Hilt's version from [Dagger's releases](https://github.com/google/dagger/releases), as rule 1.12 says: developer.android.com's setup samples pin 2.57.1, which predates the Hilt Gradle plugin's AGP 9 support in 2.59. Sources: [Dependency injection in Android](https://developer.android.com/training/dependency-injection) ("Hilt is Jetpack's recommended library for dependency injection in Android"), [Dependency injection with Hilt](https://developer.android.com/training/dependency-injection/hilt-android), [Hilt Gradle setup](https://dagger.dev/hilt/gradle-setup). **Framework choice** to start with Hilt rather than when the app crosses Google's line: "Use Hilt or manual dependency injection in simple apps. Use Hilt if your project is complex enough", for example with "Multiple screens with ViewModels" or ViewModels "scoped to the navigation back stack" ([Architecture recommendations](https://developer.android.com/topic/architecture/recommendations)), which rule 4.5 already does. Wiring by hand is a deviation.

9.4. **Bindings.** Classes the app writes take their dependencies through an `@Inject constructor`. An interface, such as a repository's or a store's, is bound to its implementation with `@Binds` in an abstract `@Module` with `@InstallIn(SingletonComponent::class)`. Objects the app can't construct itself, such as the Room database and the coroutine dispatchers (rule 2.10), come from `@Provides` functions, with a qualifier annotation for each dispatcher. App-wide objects are `@Singleton`. Source: [Dependency injection with Hilt](https://developer.android.com/training/dependency-injection/hilt-android), [Architecture recommendations](https://developer.android.com/topic/architecture/recommendations) ("Use dependency injection best practices, mainly constructor injection when possible").

9.5. **ViewModels.** Each ViewModel is `@HiltViewModel` with an `@Inject constructor`. The screen-level composable (rule 2.6) gets it with `hiltViewModel()` from `androidx.hilt:hilt-lifecycle-viewmodel-compose`, not `hilt-navigation-compose`: the `hiltViewModel()` APIs moved to the new artifact "such that they can be used without transitively depending on `androidx.navigation`" ([Hilt releases, 1.3.0](https://developer.android.com/jetpack/androidx/releases/hilt)). Called inside a `NavEntry`, it is scoped to that entry by rule 4.5's decorator: "Scope ViewModels to `NavEntry`s using `rememberViewModelStoreNavEntryDecorator`. Use `hiltViewModel` inside the provider for that `NavEntry` to retrieve the associated ViewModel" ([Use Hilt with other Jetpack libraries](https://developer.android.com/training/dependency-injection/hilt-jetpack)). A ViewModel that needs its navigation key takes it by assisted injection: `@HiltViewModel(assistedFactory = …Factory::class)` on a class with an `@AssistedInject constructor(@Assisted val key: …)` and an `@AssistedFactory` interface, obtained with `hiltViewModel<…ViewModel, …ViewModel.Factory>(creationCallback = { factory -> factory.create(key) })` ([Navigation 3: Passing arguments](https://developer.android.com/guide/navigation/navigation-3/recipes/passingarguments), Hilt recipe). "Unlike SavedStateHandle, the values passed through assisted parameters to a Hilt View Model do not get saved to disk" ([Hilt View Models](https://dagger.dev/hilt/view-model)), so state that must survive process death still uses `SavedStateHandle` (rule 2.11).
