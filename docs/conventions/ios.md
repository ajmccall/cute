# iOS convention reference

The rules an iOS builder follows and an iOS reviewer checks against. Cite a rule by its number, for example "rule 4.3". A review finding names the rule behind it where there is one. A breach of a required rule (Required rules, below) is a required finding; a breach of any other rule, which is advisory, is an optional finding for the builder only; a finding with no rule behind it isn't rejected, but it isn't a required finding either. The ten sections match the Android reference, so "section 4" means navigation on both.

## How to read this reference

- **Assumes** the current stable toolchain on 2026-10-02: Xcode 27, with Swift 6.4 and the iOS 27 SDK ([Xcode 27 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)). Update this line, and any rule it affects, when a new Xcode leaves beta.
- These rules are guidance. A rule gives its source where that helps: developer.apple.com (documentation, the Human Interface Guidelines and WWDC sessions) or swift.org, or a first-party tool's own help output, for example `xcrun simctl help` or `xcodebuild -help`, cited as the command that prints it, with the Xcode version it was read on. A new rule needn't have a source, and the sources already given stay. Samples and blogs may illustrate a rule.
- Quoted words are copied exactly from the cited page. A rule claims no more than its source says; anything it adds is labelled **Framework choice**.
- A rule that settles something Apple leaves open, or that departs from Apple's guidance, is labelled **Framework choice**: a judgement call the framework makes, which the framework steward can change. A rule isn't labelled only because it gives no source. Where Apple offers more than one current option, the Framework choice names the alternative, and a project that uses the alternative isn't departing from the rule, so it records no deviation.
- A project never edits this reference. It departs from a required rule, including the section 9 third-party decision, by recording a deviation, which the product owner approves: in `AGENTS.md`'s **Deviations** for the whole app, or in the feature's **Deliberate platform differences** for one feature. Departing from an advisory rule needs no deviation.
- A rule whose API needs a minimum OS is labelled with it, for example **iOS 17+**. The project decides its minimum OS. If that minimum is lower than a rule's label, the builder raises it as a decision rather than working around it. Rules without a label use APIs available from iOS 13.
- The builder's own rules apply and aren't repeated: native, with nothing shared with the other platform, and the command-line build (`AGENTS.md`). Section 9 holds the default dependencies.
- These are rules, not tutorials. Follow the source for detail.

## Required rules

A rule is **required** when a breach harms a person using the app (they can't read, reach or leave something, or they lose saved data), commits the app to something without the product owner, or breaks parallel sessions. A breach of a required rule is a required finding. Architecture, test method, project setup, look and command-line how-to are advisory. The eight required rules, each labelled **Required** in place:

- 2.7: the SwiftData schema is versioned from the first release, so saved data survives an upgrade.
- 4.3: the system Back button, and the edge swipe back.
- 4.5: a full-screen cover shows its own visible close control.
- 5.1: Dynamic Type, up to the largest accessibility sizes.
- 5.2: hit targets of 44 pt, never under 28 pt.
- 5.3: a VoiceOver label on every control and meaningful image.
- 8.8: a Simulator of its own per session.
- 9.1, the third-party decision only: no third-party package without the product owner's decision. The preference order itself is advisory.

Every other rule is advisory: a builder follows it by default, a breach is an optional finding for the builder only, and departing from it needs no deviation.

## Design versus platform

- The project's design source, named in `AGENTS.md`, owns the look: colour, type, shape, layout and custom components.
- This reference owns the behaviour that people and the OS rely on: navigation and back gestures, accessibility (Dynamic Type, VoiceOver, hit targets) and system integration.
- When the design really clashes with a rule here, the builder doesn't settle it. It sends the clash to the product owner as a decision in the ticket.

## 1. Project structure

1.1. The app is an Xcode project with an app target, a unit-test target and a UI-test target. Source: [Adding tests to your Xcode project](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project#Overview).

1.2. The entry point is one type that conforms to `App`, marked `@main`, whose `body` declares its scenes (`WindowGroup`). **iOS 14+**. Source: [App](https://developer.apple.com/documentation/swiftui/app), [App organization](https://developer.apple.com/documentation/swiftui/app-organization).

1.3. Colours and images live in the asset catalog. Source: [Managing assets with asset catalogs](https://developer.apple.com/documentation/xcode/managing-assets-with-asset-catalogs). The app icon is a single Icon Composer file, which supports Liquid Glass, and from which Xcode generates icons for earlier OS releases. **Framework choice** between Apple's two current options ([Creating your app icon using Icon Composer](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer), [Adopting Liquid Glass: App icons](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass#App-icons)). Alternative: an app icon set in the asset catalog, which keeps an existing icon unchanged on earlier releases. If the design source supplies the icon in one of these forms, use that form.

1.4. User-facing strings live in a String Catalog (`.xcstrings`), even before the app is localised. Source: [Localizing and varying text with a string catalog](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog).

1.5. Names follow the Swift API Design Guidelines. Source: [API Design Guidelines: Naming](https://www.swift.org/documentation/api-design-guidelines/#naming).

1.6. Keep main-actor default isolation on, as Xcode 26 and later set it for new app projects, and turn on Approachable Concurrency, which Apple recommends for all projects. Source: [WWDC25: Embracing Swift concurrency](https://developer.apple.com/videos/play/wwdc2025/268/), [Build settings reference: Default Actor Isolation](https://developer.apple.com/documentation/xcode/build-settings-reference#Default-Actor-Isolation).

1.7. Use the Swift 6 language mode, so data races are compile-time errors. **Framework choice**: the mode is opt-in ([Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/)). Alternative: Swift 5 mode with complete concurrency checking.

1.8. Group source files by feature, with shared code in its own group. **Framework choice**: Apple doesn't prescribe a folder layout.

## 2. Architecture layers and state holders

2.1. Apple doesn't prescribe layers or a pattern such as MVVM. **Framework choice**: keep three parts. Views only display state and send user actions. Observable model types hold screen and app state and the logic that changes it. Services (data, system frameworks) sit behind protocols (rule 9.4) and know nothing about views. Alternative: views that read model data directly, as in Apple's samples, with no screen-level model. Context: Apple says a data model separates the data from the views, which "improves testability" ([Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app#Overview)).

2.2. State shared between views lives in a class marked `@Observable`. The view that creates it owns it with `@State`; other views receive it through their initialiser or the environment, and use `@Bindable` to bind to its properties. **iOS 17+**. Source: [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app#Make-model-data-observable), [Observation](https://developer.apple.com/documentation/observation).

2.3. Use the `Observable` macro rather than `ObservableObject`, `@Published` and `@StateObject` in new code. Keep the older types only if the project's minimum OS is below iOS 17. **iOS 17+**. Source: [Migrating from the Observable Object protocol to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro).

2.4. State that belongs to one view is `@State private`. A child that must change it receives a `@Binding`. Source: [State: Share state with subviews](https://developer.apple.com/documentation/swiftui/state#Share-state-with-subviews), [Binding](https://developer.apple.com/documentation/swiftui/binding).

2.5. Async work tied to a view's lifetime starts in `.task`, which SwiftUI cancels when the view goes away. **iOS 15+**. Source: [task(name:priority:file:line:_:)](https://developer.apple.com/documentation/swiftui/view/task(name:priority:file:line:_:)).

2.6. State that views observe is main-actor isolated: under rule 1.6 by default, otherwise mark the type `@MainActor`. Slow work runs off the main actor in async service code. Source: [MainActor](https://developer.apple.com/documentation/swift/mainactor), [WWDC25: Embracing Swift concurrency](https://developer.apple.com/videos/play/wwdc2025/268/).

2.7. **Required.** **Data saved with SwiftData.** Version the schema from the first release: the models live in a `VersionedSchema`, "an interface for describing a specific version of a schema, including the models it contains", listed in a `SchemaMigrationPlan`, "an interface for describing the evolution of a schema and how to migrate between specific versions", and the container is created with that plan. Each later schema change adds its version to the plan, with a migration stage. **iOS 17+**. Source: [VersionedSchema](https://developer.apple.com/documentation/swiftdata/versionedschema), [SchemaMigrationPlan](https://developer.apple.com/documentation/swiftdata/schemamigrationplan). **Framework choice** to version from the start. Apple doesn't document what SwiftData does with a store written by a later schema, or why a store won't open. On the iOS 27.0 Simulator, a store written by a later schema version opened without error under the earlier schema and its plan, and was migrated down, losing what the later version had added. A store whose main file wasn't a database threw only `SwiftDataError.loadIssueModelContainer`, with no underlying error. So a ticket that must keep such stores checks an existing store before opening it: Core Data's [`metadataForPersistentStore(type:at:options:)`](https://developer.apple.com/documentation/coredata/nspersistentstorecoordinator/metadataforpersistentstore(type:at:options:)) "returns the metadata of a specific type of persistent store at the provided location", and [`isConfiguration(withName:compatibleWithStoreMetadata:)`](https://developer.apple.com/documentation/coredata/nsmanagedobjectmodel/isconfiguration(withname:compatiblewithstoremetadata:)) checks it against each version in the plan. This check reads the store's metadata only, so damaged pages further in pass it, and the open then fails. **Framework choice**.

## 3. Building UI

3.1. The design source comes first. If the project names none, use stock SwiftUI components and system styles as the HIG describes them. Source: [HIG: Components](https://developer.apple.com/design/human-interface-guidelines/components). Restyling them is a look decision, which belongs to a design source, not to the builder.

3.2. Let standard bars, sheets, popovers and controls take Liquid Glass automatically. Don't rebuild them with custom chrome. Use `glassEffect` only for custom controls, sparingly, and never in the content layer. **iOS 26+** (`glassEffect`). Source: [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass#Visual-refresh), [Applying Liquid Glass to custom views](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views), [HIG: Materials](https://developer.apple.com/design/human-interface-guidelines/materials#Liquid-Glass).

3.3. **Colour tokens.** Use system and semantic colours by default. A custom colour is a Color Set in the asset catalog, with light, dark and increased-contrast variants. No hard-coded colour values in views. Source: [HIG: Color](https://developer.apple.com/design/human-interface-guidelines/color#Best-practices), [HIG: Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode#Dark-Mode-colors).

3.4. **Type tokens.** Use the system text styles (`.body`, `.headline` and so on). Apply a custom font with `Font.custom(_:size:relativeTo:)`, naming the text style it stands in for, so it scales with Dynamic Type like that style. Don't use `Font.custom(_:fixedSize:)` for text, because it doesn't scale. **iOS 14+**. Source: [Applying custom fonts to text](https://developer.apple.com/documentation/swiftui/applying-custom-fonts-to-text#Apply-a-font-supporting-dynamic-sizing), [custom(_:fixedSize:)](https://developer.apple.com/documentation/swiftui/font/custom(_:fixedsize:)) ("does not scale with Dynamic Type").

3.5. **Size tokens.** Spacing and sizes that should grow with text use `@ScaledMetric`. **iOS 14+**. Source: [ScaledMetric](https://developer.apple.com/documentation/swiftui/scaledmetric), [Applying custom fonts to text: Scale padding using scaled metric](https://developer.apple.com/documentation/swiftui/applying-custom-fonts-to-text#Scale-padding-using-scaled-metric) ("a scaled value that changes automatically with accessibility settings").

3.6. Tokens that aren't asset-catalog colours (for example spacing or corner radii from a design system) are passed down as custom environment values declared with `@Entry`. **Framework choice** of mechanism; the API is at [Entry()](https://developer.apple.com/documentation/swiftui/entry()) and [EnvironmentValues](https://developer.apple.com/documentation/swiftui/environmentvalues). Alternative: a static constants type.

3.7. **Custom components.** When a custom design changes how a stock control looks but not what it does, write a style (`ButtonStyle`, `ToggleStyle` and so on) for the stock control. A `ButtonStyle` keeps the button's standard interaction behaviour and changes only its appearance. Otherwise compose views, and share repeated styling as a `ViewModifier` behind a `View` extension. Source: [ButtonStyle](https://developer.apple.com/documentation/swiftui/buttonstyle), [ViewModifier](https://developer.apple.com/documentation/swiftui/viewmodifier).

3.8. Every custom component meets section 5 itself: it scales with Dynamic Type, has a VoiceOver label and the right traits, and has a large enough hit target. Source: [HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility).

3.9. Removed in v4: a project names the appearances it supports in `AGENTS.md`.

3.10. A `List` `swipeActions` action that opens a confirmation may close the revealed action before the confirmation appears. Test that lifecycle before treating a retained action as a requirement. **Framework choice**, based on an iOS 27.0 Simulator observation: accept stock SwiftUI behaviour unless the design source requires otherwise; a retained action needs a custom control or UIKit alternative and is a decision for the product owner. Source for the stock API: [swipeActions(edge:allowsFullSwipe:content:)](https://developer.apple.com/documentation/swiftui/view/swipeactions(edge:allowsfullswipe:content:).

## 4. Navigation and back behaviour

4.1. Hierarchical navigation uses `NavigationStack` with value-based `navigationDestination(for:)`. When code needs to push, pop or restore the stack (for example deep links or state restoration), hold the path in state and pass it to `NavigationStack(path:)`. Otherwise the stack manages its own state. Don't use `NavigationView`. **iOS 16+**. Source: [NavigationStack: Manage navigation state](https://developer.apple.com/documentation/swiftui/navigationstack#Manage-navigation-state), [navigationDestination(for:destination:)](https://developer.apple.com/documentation/swiftui/view/navigationdestination(for:destination:)), [NavigationView](https://developer.apple.com/documentation/swiftui/navigationview) ("Use NavigationStack and NavigationSplitView instead").

4.2. Top-level sections use a `TabView`, declared with `Tab` values. **iOS 18+** for `Tab`. Source: [TabView](https://developer.apple.com/documentation/swiftui/tabview), [Tab](https://developer.apple.com/documentation/swiftui/tab), [HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars).

4.3. **Required.** Use the system Back button, and keep the edge swipe back. If the design source styles the Back button, the custom button must look like the standard one, behave like it (one tap goes back one level), and leave the edge swipe working. A design that drops the Back button or the edge swipe is a clash for the product owner (see **Design versus platform**). Source: [HIG: Toolbars, Navigation](https://developer.apple.com/design/human-interface-guidelines/toolbars#Navigation) ("Use the standard Back and Close buttons… If you create a custom version of either, make sure it still looks the same, behaves as people expect, and matches the rest of your interface"), [HIG: Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios#Best-practices), [HIG: Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures#Custom-gestures).

4.4. A self-contained task is shown in a sheet, with an explicit Cancel button on the leading edge of its toolbar and a Done (or Save) button on the trailing edge. Without unsaved changes, the person can also dismiss the sheet by swiping down. While there are unsaved changes, block the swipe with `interactiveDismissDisabled`, and when the person taps Cancel, confirm with an action sheet (`confirmationDialog`) before discarding. **iOS 15+**. Source: [HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets#iOS-iPadOS) ("The Done button dismisses a sheet after completing a task or explicitly saving changes"), [HIG: Modality](https://developer.apple.com/design/human-interface-guidelines/modality#Best-practices), [interactiveDismissDisabled(_:)](https://developer.apple.com/documentation/swiftui/view/interactivedismissdisabled(_:)), [confirmationDialog(_:isPresented:titleVisibility:actions:)](https://developer.apple.com/documentation/swiftui/view/confirmationdialog(_:ispresented:titlevisibility:actions:)-87n66). **Framework choice, a known gap against the HIG.** The HIG asks for the confirmation when people begin swiping to dismiss a sheet with unsaved changes. SwiftUI before iOS 27 documents no way to detect that attempt, so under this rule the swipe simply stops. UIKit's [`presentationControllerDidAttemptToDismiss(_:)`](https://developer.apple.com/documentation/uikit/uiadaptivepresentationcontrollerdelegate/presentationcontrollerdidattempttodismiss(_:)) would close the gap, but the platform rules make the UI SwiftUI, so this reference doesn't use it. iOS 27 adds [`dismissalConfirmationDialog(_:shouldPresent:actions:)`](https://developer.apple.com/documentation/swiftui/view/dismissalconfirmationdialog(_:shouldpresent:actions:)), whose page speaks of dismissing "the window for this view" and doesn't say whether that includes a sheet. It is untested here, and isn't part of this rule.

4.5. **Required.** A full-screen presentation (`fullScreenCover`) has no system Back, so it shows its own visible close control, which stays on screen at every text size: keep it outside the scrolling content, for example in a top `safeAreaInset`. VoiceOver's escape gesture also closes it (`accessibilityAction(.escape)`). Source: [HIG: Modality](https://developer.apple.com/design/human-interface-guidelines/modality#Best-practices) ("Always give people an obvious way to dismiss a modal view"), [fullScreenCover(isPresented:onDismiss:content:)](https://developer.apple.com/documentation/swiftui/view/fullscreencover(ispresented:ondismiss:content:)), [AccessibilityActionKind.escape](https://developer.apple.com/documentation/swiftui/accessibilityactionkind/escape) ("dismisses a modal view or cancels an operation"). **Framework choice**: keeping the control on screen while the content scrolls.

## 5. Accessibility

5.1. **Required.** All text supports Dynamic Type, up to the largest accessibility sizes. Use text styles (rule 3.4), and let layouts wrap or reflow rather than truncate. Source: [HIG: Typography, Supporting Dynamic Type](https://developer.apple.com/design/human-interface-guidelines/typography#Supporting-Dynamic-Type).

5.2. **Required.** Controls have a hit target of 44 × 44 pt by default and never less than 28 × 28 pt. Source: [HIG: Accessibility, Mobility](https://developer.apple.com/design/human-interface-guidelines/accessibility#Mobility).

5.3. **Required.** Every control and meaningful image has a VoiceOver label: `accessibilityLabel` for icon-only controls, and values, hints and traits where they help. Group related elements with `accessibilityElement(children:)`. Purely decorative images use `Image(decorative:)`. A time shown as a clock, such as "0:05" or "1:02:30", has a label that says it in words ("5 seconds", "1 hour, 2 minutes, 30 seconds"), because VoiceOver reads the bare digits as a time of day (**Framework choice**, from a review where it read a saved place that way). Source: [View accessibility modifiers](https://developer.apple.com/documentation/swiftui/view-accessibility), [Image init(decorative:bundle:)](https://developer.apple.com/documentation/swiftui/image/init(decorative:bundle:)) ("SwiftUI ignores this image for accessibility purposes"), [accessibilityElement(children:)](https://developer.apple.com/documentation/swiftui/view/accessibilityelement(children:)), [HIG: VoiceOver, Descriptions](https://developer.apple.com/design/human-interface-guidelines/voiceover#Descriptions).

5.4. Text contrast is at least 4.5:1 up to 17 pt, and 3:1 at 18 pt or bold. Never use colour alone to convey meaning. Source: [HIG: Accessibility, Vision](https://developer.apple.com/design/human-interface-guidelines/accessibility#Vision), [HIG: Color, Inclusive color](https://developer.apple.com/design/human-interface-guidelines/color#Inclusive-color).

5.5. Respect Reduce Motion: read `accessibilityReduceMotion` and replace large motion with a fade or nothing. Source: [accessibilityReduceMotion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion), [HIG: Accessibility, Cognitive](https://developer.apple.com/design/human-interface-guidelines/accessibility#Cognitive).

5.6. Once a flow has UI tests, every scenario calls `try app.performAccessibilityAudit()`, never `try?`, which throws its failures away. **iOS 17+**. **Framework choice** to require it; the API and its use are at [performAccessibilityAudit(for:_:)](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:)), [WWDC23: Perform accessibility audits for your app](https://developer.apple.com/videos/play/wwdc2023/10035/).

## 6. Unit testing

6.1. Unit tests use Swift Testing: `import Testing`, `@Test` functions, `#expect` for checks and `#require` to stop a test early. Source: [Swift Testing](https://developer.apple.com/documentation/testing), [Defining test functions](https://developer.apple.com/documentation/testing/definingtests), [Expectations and confirmations](https://developer.apple.com/documentation/testing/expectations), [WWDC24: Meet Swift Testing](https://developer.apple.com/videos/play/wwdc2024/10179/).

6.2. UI tests and performance tests use XCTest (with XCUIAutomation for UI), because Swift Testing doesn't support them. Source: [Testing](https://developer.apple.com/documentation/xcode/testing) ("Xcode continues to include XCTest to facilitate writing UI tests"), [WWDC24: Meet Swift Testing](https://developer.apple.com/videos/play/wwdc2024/10179/) ("continue using XCTest for … UI automation APIs … or performance testing APIs").

6.3. Unit tests cover models and logic directly, not views. Most of a project's tests are fast, well-isolated unit tests. Source: [Testing](https://developer.apple.com/documentation/xcode/testing) (test pyramid), [Adding tests: Write a unit test](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project#Write-a-unit-test).

6.4. Cases that differ only in input are one parameterised test, `@Test(arguments:)`. Source: [Implementing parameterized tests](https://developer.apple.com/documentation/testing/parameterizedtesting).

6.5. Async code is tested with `async` test functions. Events that should happen use `confirmation`. Source: [Testing asynchronous code](https://developer.apple.com/documentation/testing/testing-asynchronous-code#Confirm-that-an-event-happens).

6.6. Unit tests run inside the app: "The app process hosts the execution of your tests; tests are executed after receiving the applicationDidFinishLaunching notification" ([Running Tests and Viewing Results](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/05-running_tests.html), archived). So the `App` type, and the services it creates (rule 9.3), run during the tests, and whatever the app does at launch, such as opening its saved data, also happens then. The handoff says how the tests keep away from the app's real data. **Framework choice**.

6.7. **When a ticket changes saved data.** Rules 6.8 to 6.10 apply to a ticket that adds or changes a write to saved data, or changes what the app does with a damaged store. They run on the real SwiftData store (rule 2.7), each in its own new temporary folder, away from the app's real data (rule 6.6). A stub store, including one that holds a write until the test releases it, and state a view model kept can't show what reached the disk, so neither is evidence for these rules. **Framework choice**, from reviews where stubs passed and the store disagreed.

6.8. **A write that can be cancelled** (for example when leaving a screen cancels its `.task` while the write runs) is tested cancelled at two points: just before the real store saves, and just after. Wrap the real store in a test store that forwards to it and waits on a gate at either point, and cancel the calling task there. After each, compare what the model types hold, and what the screen shows, with what the store holds, asserting every field the write saves, including a field a ticket adds to an existing write. Then reopen the store and compare again. A task cancelled after the save has still saved, so code that updates its state only when the task wasn't cancelled leaves the screen behind the store. Cover the cases with one parameterised test (rule 6.4). **Framework choice**.

6.9. **Keeping files when damage is found.** Where a ticket requires the store's files to be kept rather than deleted, moved, reset or replaced, show it on the store the app actually opens, at each point the ticket names, such as at launch and while running. Checkpoint the store's write-ahead log into the main file, damage a page of the main file, run the access, and compare the main file and each companion file (`-wal`, `-shm`) before and after, by bytes and inode. The `-shm` file's reader bookkeeping may change, and an assertion allows for it. **Framework choice**.

6.10. **Damage fixtures.** Releasing a `ModelContainer` can checkpoint the store after the test has moved on, writing over damage injected in the meantime: on the Simulator, a seed container released before the damage was written put the database's pages back over it. So seed in a separate folder, keep the seed's container alive with `withExtendedLifetime` until its files have been copied into the test's own folder, damage the copy, and `#require` the exact damaged bytes before the access under test. **Framework choice**; Apple doesn't document when a container checkpoints.

## 7. Command-line build

7.1. Build and run the tests with `xcodebuild`, naming the scheme and a Simulator destination, the session's own device by its UDID (rule 8.8):

```sh
xcodebuild -scheme <App> -destination 'platform=iOS Simulator,id=<UDID>' build
xcodebuild -scheme <App> -destination 'platform=iOS Simulator,id=<UDID>' test
```

Source: [Running tests and interpreting results](https://developer.apple.com/documentation/xcode/running-tests-and-interpreting-results#Run-tests-from-a-test-plan) (`xcodebuild test -scheme`), `xcodebuild -help` (`-destination`, "a comma-separated set of key=value pairs describing the destination to use"; Xcode 27), [TN2339: Building from the command line with Xcode](https://developer.apple.com/library/archive/technotes/tn2339/_index.html) (the Simulator keys `name`, `id` and `OS`, in Table 3 and Listing 15; archived, but still Apple's only page for the keys).

7.2. Choose the device type and the OS version from `xcrun simctl list devicetypes` and `xcrun simctl list runtimes`, and create the session's own device from them (rule 8.8). Record in the handoff the destination, the device type, the OS version and the runtime build, which `xcrun simctl getenv <UDID> SIMULATOR_RUNTIME_BUILD_VERSION` prints, so a reviewer can create a device like it on another Mac, where the UDID names nothing. The runtime build tells apart two runtimes with one identifier (for example a beta and a release of the same OS version), which `OS=` can't. Source: `xcrun simctl help list`, `xcrun simctl help create` and `xcrun simctl help getenv` (Xcode 27), and TN2339 for the `OS` and `id` keys (rule 7.1). **Framework choice** to record the device type, OS version and runtime build.

7.3. Record `xcodebuild -version` in the handoff, so a reviewer knows which toolchain built it. **Framework choice**.

7.4. If the project has test plans, run them with `-testPlan`. Source: [Organizing tests to improve feedback: Run tests from the command line](https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback#Run-tests-from-the-command-line).

7.5. The test run a builder hands off with builds from a new, empty `-derivedDataPath <folder>`, so that an incremental build can't hide a failure that the reviewer's clean build shows. **Framework choice**, from a review where the builder's tests all passed in an incremental build and the clean build of the test target failed.

7.6. Evidence from a test run names how many tests ran, from its result bundle (`-resultBundlePath <path>`): `xcrun xcresulttool get test-results summary --path <path>` prints `totalTestCount`. A run that ran no tests still prints `TEST SUCCEEDED`, and counts as a failure. In `-only-testing`, a Swift Testing test's identifier ends in `()`, as `<target>/<suite>/<test>()`; without them the filter matches nothing. `test-without-building` runs whatever test binary the last build left, so build in the same run, or use `test`. Source: `xcrun xcresulttool help get test-results summary` and `xcodebuild -help` (Xcode 27). **Framework choice**, from sessions where a mistyped filter and a stale binary each reported success.

7.7. A failed test can look like a hang: `xcodebuild` then collects diagnostics, for up to 600 seconds on this toolchain. Pass `-collect-test-diagnostics never -test-timeouts-enabled YES -maximum-test-execution-time-allowance <seconds>`, so a failure reports at once and a stuck test stops. Run the whole suite with `-parallel-testing-enabled NO` as well, not only UI scenarios (rule 8.6): parallel testing runs the tests on clones of the Simulator, and on a loaded machine the clones stall timing tests until they fail. Source: `xcodebuild -help` (Xcode 27). **Framework choice**, the serial run from a review where a parallel run failed 16 of 284 tests, each from a 41-second stall, and the serial rerun passed them all.

## 8. Command-line Simulator screenshots

8.1. Boot the session's own Simulator (rule 8.8), then install and launch the build with `xcrun simctl boot`, `xcrun simctl install` and `xcrun simctl launch`. Apple documents `simctl` for starting simulated devices and points to `xcrun simctl help` for the rest ([Interacting with devices using the command line: Start simulated devices](https://developer.apple.com/documentation/xcode/interacting-with-devices-using-the-command-line#Start-simulated-devices)). `install` and `launch` are in `xcrun simctl help install` and `xcrun simctl help launch` (Xcode 27). **Framework choice** between Apple's two command-line routes. Alternative: `devicectl device install app` and `devicectl device process launch` ([#Install-apps-on-devices](https://developer.apple.com/documentation/xcode/interacting-with-devices-using-the-command-line#Install-apps-on-devices), [#Launch-apps-on-devices](https://developer.apple.com/documentation/xcode/interacting-with-devices-using-the-command-line#Launch-apps-on-devices)). The launch section covers "a simulated or physical device", but neither the install section nor `xcrun devicectl help device install app` says that install works on a simulated device, so try it on one before relying on it.

8.2. Take each screenshot with `xcrun simctl io <UDID> screenshot <file>.png`. Source: [Simulator User Guide: Taking a screenshot or recording a video using the command line](https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/iOS_Simulator_Guide/InteractingwiththeiOSSimulator/InteractingwiththeiOSSimulator.html) (retired guide), and `xcrun simctl help io` ("Save a screenshot of the booted device to screenshot.png: simctl io booted screenshot screenshot.png"; Xcode 27).

8.3. Before taking screenshots, fix the status bar with `xcrun simctl status_bar <UDID> override` (for example `--time 9:41`), and clear it afterwards. Source: [WWDC20: Become a Simulator expert](https://developer.apple.com/videos/play/wwdc2020/10647/).

8.4. When a criterion needs dark appearance or a large text size, set them with `xcrun simctl ui <UDID> appearance dark` and `xcrun simctl ui <UDID> content_size <size>`. Source: `xcrun simctl help ui` (`appearance [light | dark]` and `content_size`; Xcode 27). After changing the text size, relaunch the app with `xcrun simctl launch --terminate-running-process` before the screenshot, because a running app's stock navigation bar can clip its large title until the next launch. **Framework choice**. When the screenshot needs state that a relaunch would lose (held only in memory), build that state at the default text size with the native UI test (rule 8.6), change the text size while the test waits, and check that the large title isn't clipped in the screenshot. **Framework choice**. Building the state at the largest accessibility size instead stalled the test on Xcode 27: with an alert's keyboard up, each step waited 60 seconds for app animations to finish. Apple documents the same settings in Device Hub ([Configuring the environment of a simulated device](https://developer.apple.com/documentation/xcode/configuring-the-environment-of-a-simulated-device)).

8.5. Name each screenshot after the ID of the acceptance criterion it shows, as `<feature>-C<n>`, attach it to the ticket's pull request and list it there under each criterion. Never commit it. One screenshot can show several criteria: name it after all of them, for example `saved-items-C1-C2.png`. For a criterion of a ticket that changes no app behaviour, which has no ID, use a short name for the criterion. **Framework choice**. Alternative to rules 8.1 and 8.2, once UI tests exist: attach `XCTAttachment` screenshots from the UI test ([Adding attachments to tests, activities, and issues](https://developer.apple.com/documentation/xctest/adding-attachments-to-tests-activities-and-issues)).

8.6. `simctl` manages lifecycle and screenshots but can't scroll, tap or type. Use maintained XCUITest scenarios for stable review interactions. The test launches the production app, drives it with `tap()`, `typeText(_:)` and `swipeUp(velocity:)`, waits for elements with `waitForExistence(timeout:)`, and asserts the action's result. `isHittable` can be true for an element scrolled off screen, as a title was at the largest text size, so scroll it into view before asserting on it, and check the screenshot. Retain useful screenshots with `XCTAttachment(screenshot: XCUIScreen.main.screenshot())` and `.keepAlways`; successful tests otherwise discard attachments. Run selected scenarios on the session's own device, named by its UDID (rules 7.1 and 8.8), with `-parallel-testing-enabled NO`, `-only-testing:<UI test target>/<class>` and `-resultBundlePath <path>`. Export screenshots with `xcrun xcresulttool export attachments --path <path> --output-path <folder>` and name them after their criteria (rule 8.5). One-off exploratory tests may remain temporary; return a durable regression and its reproduction sequence to the builder when exploration finds a defect. Source: [tap()](https://developer.apple.com/documentation/xcuiautomation/xcuielement/tap()), [typeText(_:)](https://developer.apple.com/documentation/xcuiautomation/xcuielement/typetext(_:)), [waitForExistence(timeout:)](https://developer.apple.com/documentation/xcuiautomation/xcuielement/waitforexistence(timeout:)), [swipeUp(velocity:)](https://developer.apple.com/documentation/xcuiautomation/xcuielement/swipeup(velocity:)), [screenshot()](https://developer.apple.com/documentation/xcuiautomation/xcuiscreenshotproviding/screenshot()), [XCTAttachment init(screenshot:)](https://developer.apple.com/documentation/xctest/xctattachment/init(screenshot:)), [Attachment Lifetime](https://developer.apple.com/documentation/xctest/adding-attachments-to-tests-activities-and-issues#Attachment-Lifetime), `xcodebuild -help` (`-parallel-testing-enabled`, `-only-testing`) and `xcrun xcresulttool help export attachments` (Xcode 27). **Framework choice** of maintained stable scenarios and `-parallel-testing-enabled NO`, which keeps appearance/text-size/status-bar setup on the named device rather than a test clone.

8.7. The Simulator has no network of its own: "it has access to the computer's resources, including the CPU, memory, and network connection" ([Simulator User Guide: Testing and Debugging in Simulator](https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/iOS_Simulator_Guide/TestingontheiOSSimulator/TestingontheiOSSimulator.html), retired guide). Taking the Simulator offline would take the Mac offline too, cutting off the session that drives it. So a criterion that needs the device offline isn't shown in a screenshot: unit tests with a stub service (rule 9.4) show it, the handoff says so, and the product owner checks it at acceptance. **Framework choice**.

8.8. **Required.** Every session that reaches a device, whatever its role, runs on a Simulator of its own, which no other session uses. Sessions on one device install the same bundle ID, so concurrent `xcodebuild test` runs overwrite each other's app and share its data container; build products are separate per worktree, but the device isn't. `booted` doesn't name a device: "If multiple devices are booted when the "booted" device is selected, simctl will choose one of them" (`xcrun simctl help`, Xcode 27). So:

- Every session creates its device when it adds its worktree, named after the worktree: `xcrun simctl create <worktree name> <device type> <runtime>`. It prints the new device's UDID (seen on Xcode 27).
- Name the device with `id=<UDID>` in every `xcodebuild` destination (rule 7.1), and with its UDID in place of `booted` in every `simctl` command: boot, install, launch, settings, screenshots and cleanup target that device only. Never boot, erase or install on a device another session or a person started.
- Remove it when the session ends, with `xcrun simctl shutdown <UDID>` and `xcrun simctl delete <UDID>`: a builder or a product session when it removes its worktree, a reviewer at cleanup.
- Automated tests and opening a human-visible Simulator window are separate capabilities.

Source: `xcrun simctl help` ("you may specify a device UDID or the special "booted" string"), `xcrun simctl help create` and `xcrun simctl help delete` (Xcode 27), and [Interacting with devices using the command line](https://developer.apple.com/documentation/xcode/interacting-with-devices-using-the-command-line). **Framework choice** of one device per session.

## 9. Dependencies

This section is the framework's default. An app may override any of it by recording a deviation (How to read this reference).

9.1. **Required (third-party decision).** **Preference order.** Build on these, in order:

1. **Apple's own frameworks and packages**: the SDK's frameworks and any Swift package Apple publishes officially, such as Swift Collections or Swift Algorithms. These need no decision.
2. **A highly respected third-party package**, widely used, actively maintained and stable, where the first tier doesn't offer what a ticket needs. It needs a one-line decision in the ticket, naming the package and what its documentation says it brings, which the product owner approves with the ticket.
3. **Hand-written code**, where neither does.

Custom design-system components are expected; the order governs what they are built on. Packages are added with Swift Package Manager at their latest stable release, with the Up to Next Major Version rule; never copy a version from a sample, which drifts behind the stable releases. **Framework choice**; for the route: [Adding package dependencies to your app](https://developer.apple.com/documentation/xcode/adding-package-dependencies-to-your-app#Add-a-package-dependency).

9.2. **Dependency listing.** The handoff lists every package the build adds compared with `main`, from the project's `Package.resolved`, which "lists the specific Git commits to which each package dependency resolves", including packages that another package brings with it. It marks each one first tier or third-party, so the product owner can confirm any that no decision named, or query a first-tier one. **Framework choice**; source: [Adding package dependencies to your app: Coordinate package versions across your team](https://developer.apple.com/documentation/xcode/adding-package-dependencies-to-your-app#Coordinate-package-versions-across-your-team).

9.3. Wire dependencies by hand. Create services and app-wide models in the `App` type, pass them into initialisers, and put shared `@Observable` objects in the environment with `.environment(_:)`. No dependency-injection framework. **iOS 17+** (for the `Observable` overload of `.environment(_:)`). Source: [Managing model data in your app: Create the source of truth](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app#Create-the-source-of-truth-for-model-data) ("You can also create a state object in your top-level App instance"), [environment(_:)](https://developer.apple.com/documentation/swiftui/view/environment(_:)), [Environment: Get an observable object](https://developer.apple.com/documentation/swiftui/environment#Get-an-observable-object).

9.4. Each service is used through a protocol, so tests can pass in a stub. Source: [Adding tests: Write a unit test](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project#Write-a-unit-test) ("Replace complex dependencies with stubs"), [The Swift Programming Language: Protocols](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/protocols/).

## 10. Release measures

How an iOS builder measures an app release's product outcomes. Record each figure under **Product outcomes** in the ticket's pull request, with the device or Mac, its OS version and `xcodebuild -version` (rule 7.3).

10.1. **Cold start.** Measure on a physical device only, named by `id=<UDID>` in the destination (rule 7.1). Without one, cold start reads "not measured". Source: [Improving your app's performance: Profile your app](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance#Profile-your-app) ("You get higher-fidelity measurements by profiling on a device instead of the simulator"). **Framework choice** to record no Simulator figure.

10.2. Measure launch with a UI test in a performance test plan: `measure(metrics: [XCTApplicationLaunchMetric()]) { XCUIApplication().launch() }`. Run it with `xcodebuild test -testPlan <performance test plan> -destination 'platform=iOS,id=<UDID>' -resultBundlePath <path>` (rule 7.4), and read the values with `xcrun xcresulttool get test-results metrics --path <path>`. Record the average of the iterations. The scheme builds for testing with the Release configuration, with "Debug executable" off, and the test plan turns off code coverage and the runtime sanitizers. Source: [XCTApplicationLaunchMetric](https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric) ("A metric to record the application launch duration for a performance test"), [init(waitUntilResponsive:)](https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric/init(waituntilresponsive:)) ("records the time for an app to display its first frame to screen"), [Writing and running performance tests](https://developer.apple.com/documentation/xcode/writing-and-running-performance-tests) ("Configure your scheme to build for testing using the Release build configuration, and turn off the “Debug executable” setting. Configure your test plan to disable code coverage and the runtime sanitization options"), and `xcrun xcresulttool help get test-results` ("metrics: Get performance metrics"; Xcode 27). **Framework choice** to record the average.

10.3. **Download and install size.** Archive a Release build, then export it with `xcodebuild -exportArchive -archivePath <archive> -exportPath <folder> -exportOptionsPlist <plist>`, where the plist sets `thinning` to `<thin-for-all-variants>` and `method` to `debugging`, which needs only a development certificate. The export writes `App Thinning Size Report.txt`. Record the largest variant's compressed size as the download size and its uncompressed size as the install size. The export is signed, so it needs the project's signing team; without one, both read "not measured". Source: [Reducing your app's size: Automate the generation of the app size report](https://developer.apple.com/documentation/xcode/reducing-your-app-s-size#Automate-the-generation-of-the-app-size-report) ("Be sure to include the `thinning` key, with `<thin-for-all-variants>` as the value") and [Create the app size report](https://developer.apple.com/documentation/xcode/reducing-your-app-s-size#Create-the-app-size-report) ("The uncompressed size is equivalent to the size of the installed app on the device, and the compressed size is the download size of your app"), and `xcodebuild -help` (`method`: "Available options: app-store-connect, release-testing, enterprise, debugging …"; Xcode 27). **Framework choice** of the largest variant and the `debugging` method. Alternative: the sizes App Store Connect shows after an upload.

10.4. **Release build time.** Time a clean archive with a fresh derived data folder: `time xcodebuild clean archive -scheme <scheme> -configuration Release -archivePath <archive> -derivedDataPath <new empty folder> -showBuildTimingSummary`. Record the wall-clock time. Source: [Improving the speed of incremental builds](https://developer.apple.com/documentation/xcode/improving-the-speed-of-incremental-builds) ("pass the `-showBuildTimingSummary` option to the tool. The first time you build your project, Xcode builds everything, but subsequent builds are incremental"). **Framework choice** of a clean build with fresh derived data, so releases compare like with like.

10.5. **Yearly design changes.** A release adopts a design change when it is built with the SDK that brings it and its screens use the new design: standard components pick it up from the SDK, and custom components follow the design source. Each change's clock starts on the public release of the iOS version that brings it. Source: [Adopting Liquid Glass: See your app with Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass#See-your-app-with-Liquid-Glass) ("If your app uses standard components from SwiftUI, UIKit, or AppKit, your interface picks up the latest look and feel on the latest platform releases"), and [UIDesignRequiresCompatibility](https://developer.apple.com/documentation/bundleresources/information-property-list/uidesignrequirescompatibility) ("The system ignores this key when you build for iOS 27 or later"). **Framework choice** of the start date.

| Liquid Glass | iOS 26 | 2025-09-15 | [Apple security releases](https://support.apple.com/en-us/100100) ("iOS 26 and iPadOS 26", 15 Sep 2025) |
