# Framework changes and releases

The framework lives in its own repository, which the framework steward holds, and every consumer app takes it at a framework release by git subtree into its `framework/` folder. Changes reach it as framework tickets: a consumer never edits its own `framework/` outside its first install and its take tickets, and a lesson from a consumer's retro arrives as a framework ticket (`roles/product.md`, Retro on request).

- **Framework tickets.** The framework steward may open tickets in the framework repository's own tracker. These change framework documents only, so they have no platform parts and no builder or reviewer sessions: the steward works each one with one agent, which drafts as the product role does and asks the steward in rounds (`process.md`, People and questions). Each ticket has its own branch, `<number>-<slug>`, from `main`, which the agent works on in its ticket worktree, `../<repository folder>-<number>-<slug>`, never in the main checkout (`process.md`, Branches), and lands as one squash-merged change request that closes it.

Every change to the framework:

- adds what a consumer must change, if anything, to the **Unreleased** section of `CHANGELOG.md`;
- passes the boundary search (The `framework/` boundary, below): a case-insensitive search for the consumer apps' product terms and paths, counting a term only where it doesn't follow a letter, never inside another word, and a path only if it has a `/` and only as a whole path, where it starts a line or follows whitespace, a backtick, a quote or an opening bracket, never as the tail of a longer name. In a consumer the pre-commit hook runs it at each commit (`hooks/README.md`); in the framework's repository, where no contract names the terms, the change request's description reports a search run by hand;
- reruns `hooks/test` when it changes `hooks/`, and shows the result on the change request;
- is reviewed and merged by the framework steward. No agent merges into the framework's `main`.

**The `framework/` boundary.** `framework/` holds the generic system and names nothing specific to one app's product, and none of the project's own paths (`AGENTS.md` lists them). It may name iOS, Android, SwiftUI and Jetpack Compose. App-specific material lives in the project's own docs. The pre-commit hook searches `framework/` for the product's terms and paths at each commit that touches it (`hooks/README.md`).

**Plain core.** Roles, process, templates and convention references are plain Markdown that any agent harness can follow. A role names a published skill as its default skill (`agents-template.md`, Skills and roles). Harness-specific configuration belongs in a harness adapter, `adapters/<harness>/`, never in the core; an adapter runs `hooks/install` at session start and prints the Cost line, may say how its harness runs an orchestrator (`orchestrate.md`), and nothing in the framework requires one. Changing an adapter is a framework change, and an adapter with a self-test reruns it on its change request.

**The skills.** Matt Pocock's skills (`github.com/mattpocock/skills`) are a prerequisite that each person installs the way their harness installs skills. The framework doesn't install them, pin a version or check which copy loaded, so sessions on one ticket may run different versions, and a change upstream arrives unannounced. The only check is the session's own: one started without the skills stops and tells the human (`agents-template.md`, Skills and roles). What the roles rely on is this, and the framework steward reads it against upstream when a role misbehaves or upstream announces a change:

- Ten skills by name: `grill-with-docs`, `to-spec`, `to-tickets`, `grilling`, `retro`, `implement`, `tdd`, `diagnosing-bugs`, `code-review` and, once per project, `setup-matt-pocock-skills`.
- A model may start `grilling`, `tdd`, `diagnosing-bugs` and `code-review` itself. Only a person starts the others.
- `code-review` reviews the changes since a fixed point it is given, on two axes kept apart, Standards and Spec, each in a nested session.
- `implement` uses `tdd`, ends with `code-review` and commits to the current branch.
- `to-spec` writes user stories.

Where upstream no longer matches a line, a framework ticket changes the role page that leans on it. A role page's overrides still win over the skill.

**Releases.** The framework steward decides when to cut one. They choose its semantic version from the Unreleased entries (major when a consumer must change its own files, minor when it adds rules or roles a consumer can adopt without edits, patch for wording only), rename Unreleased to that version with its date, start a new empty Unreleased section, and tag `main` as `v<version>`.

**First install.** A project adopts the framework once, with `install`, run from a clone of the framework's repository: `./install <project path> [--boundary-terms "<terms>"] [--release v<version>] [--adapter claude-code|pi]`. It is the one change to a project's `framework/` outside a take ticket, and it isn't a ticket. Before its first change it checks every refusal, and changes nothing unless the project is a git repository with a first commit, a clean working tree, a `main` branch and an `origin` remote, with no `framework/` yet and `core.hooksPath` unset or set to `framework/hooks`; each refusal says what to fix. It works in the worktree `../<repository folder>-install-framework-v<version>`, on the branch `install-framework-v<version>` from `main`. There it runs `git subtree add --prefix=framework <framework repository> v<version> --squash`, from the clone's `origin` URL as it is, then `framework/hooks/install`, then makes one wiring commit, which the hooks check. The wiring commit holds a new `AGENTS.md` from the release's `agents-template.md`, with only the framework's URL and release, the Harness adapter row and the Boundary terms line filled in, from `--boundary-terms`, which a new `AGENTS.md` requires; with `--adapter`, it also holds that adapter's wiring (its README, Wiring it in). It reads everything it copies from the release it installs, never edits an existing `AGENTS.md`, and never commits to `main`, pushes or opens a change request. If a step fails, it removes what it made. It ends by printing what's left: the placeholders in `AGENTS.md`, by who fills them; the tracker and its binding's one-time setup; the skills; the first ticket; the push. The product owner checks the branch, runs `framework/hooks/pre-commit --range origin/main` on it, and lands it with a merge commit, never a squash: the subtree add is a merge, and a squash drops its second parent, so every later `subtree pull` fails. `--release` defaults to the newest release on `origin`, and the oldest it installs is 6.1.0. Its self-test, `test`, sits beside it; a change to `install` reruns it and shows the result on its change request.

**Checking the wiring.** Once a project has `framework/`, `./install --check <checkout> [--adapter claude-code|pi]`, run from a clone of the framework, changes nothing and reports each piece of wiring the checkout's release expects, as ok, missing or different: `core.hooksPath` set to `framework/hooks`, or the project's own pre-commit and pre-merge-commit calling `framework/hooks/pre-commit`; in `AGENTS.md`, the release `framework/` holds, the framework's repository, the Harness adapter row and the Boundary terms line; and for the adapter that row names, or `--adapter` names, its `settings.json` merged into its harness's project settings, `.claude/settings.json` or `.pi/settings.json`, where a package it lists that the project lists at another ref counts as different, as does a setting an earlier release's adapter wired in and this one has dropped, such as the skills pins from before 7.0.0, and, for Claude Code, `@AGENTS.md` in an existing `CLAUDE.md`. The release's own files are the description of its wiring: `--check` reads them from `framework/` at the checkout's HEAD, never from the clone, and the release is the one whose tag's tree `framework/` is. It takes any checkout, a ticket worktree included, checks releases from 6.1.0, and refuses a release newer than the clone. `./install --wire <checkout> [--adapter claude-code|pi]` makes the changes `--check` marks as its: it runs `framework/hooks/install` where `core.hooksPath` is unset, merges in the adapter's settings as the first install does, removes each dropped setting, adds `@AGENTS.md` to a Claude Code project's `CLAUDE.md`, and in `AGENTS.md` changes only the release's number and, with `--adapter`, a Harness adapter row that is None or still its placeholder. It changes files only in the working tree, on a branch other than `main`, never through a symbolic link, and commits nothing; on `main` it only sets the hooks path. It refuses partway through a merge or over uncommitted changes to a file it writes. What's left, such as a setting the project sets differently from the adapter, is for a person to decide, and `--check` goes on reporting it. Both exit 0 only when nothing is left to fix.

**Taking a release.** A consumer app takes a release in a ticket with no platform work. The framework steward decides when, and approves the ticket for build. No ticket is open at the take: finish or close each, and a closed one returns to an idea; the take ticket runs under the release the consumer started on. Its Schema change is "None: takes framework release <version>", and its acceptance criteria are the changelog's consumer-must-change lines for each release it takes. The builder runs `git subtree pull --prefix=framework <framework repository> v<version> --squash` on the ticket branch. The pull merges from the previous squash's split commit, not from the tree `framework/` has now, so changes the consumer sent upstream since its last take come back as the consumer's own: expect the pull to conflict, or to keep their lines twice, even when `framework/` has the tree of a commit the release contains. Whatever the merge does, `framework/` ends as the tree of the pull's squash commit. Mid-merge, before committing, the builder sets it with `git rm -rqf framework && git read-tree --prefix=framework/ -u MERGE_HEAD^{tree}`. After a merge that committed without conflicts, it checks that `git rev-parse HEAD:framework` prints `git rev-parse HEAD^2^{tree}`; where it doesn't, it runs the same command with `HEAD^2^{tree}` and amends the merge commit. It then makes the changelog's changes, and runs `install --check` on the ticket worktree from a clone of the framework (Checking the wiring): `install --wire` makes what it can, including the release named in `AGENTS.md`, and the builder makes or raises the rest. The ticket's Validation checks the take with these three, written from this paragraph rather than copied from an earlier take ticket: `git rev-parse <merge>:framework` prints the release's tree (`git rev-parse v<version>^{tree}` in the framework repository, recorded in the ticket's Notes), and `git log -1 --format=%s <merge>^2` shows the squash commit, "Squashed 'framework/' changes from …"; and `install --check <ticket worktree>` reports nothing to fix, or the ticket names each line it still reports and why. A log limited to `framework/` never lists the squash commit, because it holds the framework at its root. The ticket's change request lands with a merge commit (`process.md`, Branches).
