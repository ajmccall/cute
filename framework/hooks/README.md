# Local hooks

What the framework's pre-commit hook, `pre-commit`, checks, where it reads from, how to install it, when a commit may bypass it, and how to change it. The framework also ships `pre-merge-commit`, which runs the same checks on a clean merge commit. The checks finish in seconds: builds and tests stay with builder evidence and the reviewer's reruns, and there is no pre-push hook. The hook needs git and the `python3` that Xcode's Command Line Tools provide, which the iOS build already requires; nothing else.

- **What it checks**, on the staged content, never the working tree:
  - **Whitespace:** git's own `diff --cached --check` (trailing spaces, a space before a tab, blank lines at the end of a file, conflict markers).
  - **Schema:** each staged feature file in the app schema folder has the nine `##` sections of `schema-template.md`, spelled exactly and in order and no others; its **States** holds a `No lifecycle:` line or a state machine with its transition table; each acceptance criterion starts `**C<n>.**` with an ID unique in the file; and each `<feature>#C<n>` citation names a criterion that exists. Whether a "No lifecycle" reason holds is the reviewer's judgement, not the hook's.
  - **Boundary search:** whenever a staged path is under `framework/` or `AGENTS.md` itself is staged, the whole staged `framework/` tree is searched for the product's terms and paths (`framework-changes.md`, The `framework/` boundary). The terms are the **Boundary terms** line in `AGENTS.md`'s App settings; the paths are those its Where things live table lists outside `framework/`. A term counts only where it doesn't follow a letter, never inside another word, so a term isn't found in the middle or at the end of a longer word; it still counts at the start of an identifier, such as `<term>BoardView`, and after a digit, `_` or `-`, but not after a letter, as in camelCase `is<term>`. Examples here use `<term>`, never a real word, so that the framework never holds a term an app might choose. A path counts only if it has a `/`, so a bare filename the framework also names is never searched, and only as a whole path: where it starts a line or follows whitespace, a backtick, a quote or an opening bracket, never as the tail of a longer name. A missing Boundary terms line fails the search.
- **Merges and replayed commits.** For a clean merge commit, Git runs `pre-merge-commit` with the merge result staged and `HEAD` still at the first parent. A conflicted merge completed with `git commit` runs `pre-commit` instead. Fast-forwards create no commit and run neither hook. Cherry-picks and rebases replaying commits do not run either hook; the reviewer’s range check remains the backstop.
- **On a finished change.** `framework/hooks/pre-commit --range <base>` runs the same checks on everything `<base>...HEAD` changes, read from `HEAD`, as if the whole change were staged at once. It ignores the index and the working tree, and exits non-zero on any problem. The reviewer runs it on the change it reviews (`roles/reviewer.md`).
- **Where it reads from.** The hook reads the consumer contract, `AGENTS.md`, as staged: the App schema row's path, the other paths in Where things live, and the Boundary terms line. A Where things live cell still in its template form, `<…>`, is skipped, so that an `AGENTS.md` fresh from `agents-template.md` passes before it is filled in; the Boundary terms line isn't, and must be filled. In the framework's own repository there is no `AGENTS.md`, so only the whitespace check runs there.
- **Install.** `framework/hooks/install` sets the clone's `core.hooksPath` to the hooks folder, so every worktree of the clone runs the hook. It is idempotent: it sets the path when unset, confirms when already set there, and refuses when set elsewhere, so that it never replaces a project's own hooks. A project with hooks of its own keeps them and calls `framework/hooks/pre-commit` from both its own pre-commit and its own pre-merge-commit, propagating failures. A project whose pre-merge-commit already invokes its pre-commit need not call it twice. Every session runs the install when it starts, or its harness adapter does (`agents-template.md`, Prerequisites). A refused install stops the session, and the refusal goes to the product owner as a decision.
- **Bypass.** `git commit --no-verify` and `git merge --no-verify` skip these checks, so nothing can stop it; the rule makes it visible instead. Only a human allows a bypass. No agent commits with `--no-verify` on its own word. The commit's message ends with the trailer `Hook-bypassed: <reason>`, and the commit counts as a correction by the human role that allowed it. The reason is a lesson for a retro: a check that was wrong, or in the way.
- **Changing the hook.** `framework/hooks/test` builds throwaway repositories and commits fixtures that must pass and must fail. A change to `hooks/` reruns it and shows the result on its change request (`framework-changes.md`).
